The problem — the model is the easy part

Three questions that decide if it was real work

Can you get that number again?

Different seed, different split, different answer. Which of your improvements were real?

Which checkpoint is the good one?

You saved at the end. Validation peaked at epoch 11 and drifted down for four more.

Can it run without your repo?

A state_dict needs your model class. Serving should not import your training code.

This session is those three answers, plus the environment trap that wastes an afternoon before you even start.

Start here: which device do you actually have?

Probe it, do not trust it

def pick_device():
    if torch.cuda.is_available():
        try:
            a = torch.randn(64, 64, device="cuda")
            (a @ a).sum().item()            # force a real kernel launch
            return torch.device("cuda")
        except Exception:
            print("GPU present but kernels do not run -- using CPU")
    return torch.device("cpu")

WHYWhy the pipeline, not the model

Four things that decide whether the work survives.

Reason 1 — reproducibility is four generators, not one

def seed_everything(seed=42):
    random.seed(seed)                       # python: shuffles, sampling
    np.random.seed(seed)                    # numpy: data generation, sklearn
    torch.manual_seed(seed)                 # torch: init, dropout
    torch.cuda.manual_seed_all(seed)        # every GPU
    os.environ["PYTHONHASHSEED"] = str(seed)

Miss any one of them and "identical" runs diverge — usually just enough that you cannot tell whether your change helped or the seed did.

Log the seed with the run. A result you cannot reproduce is an anecdote; session 7 gives you somewhere to record it.

Reason 2 — the loop, written out once

for xb, yb in train_dl:
    opt.zero_grad(set_to_none=True)      # 1. clear last step's gradients
    loss = loss_fn(model(xb), yb)          # 2. forward
    loss.backward()                        # 3. backward: fill .grad
    clip_grad_norm_(model.parameters(), 1.0)  # 4. cheap insurance
    opt.step()                             # 5. update the weights
ForgetSymptom
zero_gradgradients accumulate; loss goes nowhere or explodes
model.train() / .eval()dropout active during validation — noisy, wrong scores
torch.no_grad() in evalbuilds a graph you never use; slow, memory-hungry

Every framework is this loop. Learn it once and Lightning, Trainer and accelerate stop being magic.

Reason 3 — save the model you want, not the last one

if val_auc > best:
    best = val_auc
    torch.save({"epoch": epoch, "model": model.state_dict(),
                "opt": opt.state_dict(), "val_auc": val_auc}, "best.pt")

epoch 11  train 0.1675  val 0.1452  auc 0.9879  <- saved
epoch 12  train 0.1658  val 0.1485  auc 0.9879
epoch 15  train 0.1651  val 0.1481  auc 0.9877        <- what you would have shipped
Save the optimiser too. Without it you cannot resume, and a long run that cannot resume is one power cut from starting over.
Validation wobbles. Saving at the end ships the wobble. One if ships the peak.

Reason 4 — it has to leave your laptop

The trap: torch.save(model) pickles the class by reference. Rename or move the file and the checkpoint stops loading. Save the state_dict, or export.

And always diff the outputs after export. A silent numerical difference is a production bug that no test in your training repo will catch.

Crash course — the words a training loop is made of

WordWhat it means
tensorPyTorch's array. Like a NumPy array, but it can live on a GPU and remembers how it was computed so gradients can be worked out.
batcha handful of rows processed together — 32 or 64 is typical. Bigger batches are faster per row and use more memory.
epochone full pass over the training data. Ten epochs = the model saw every row ten times.
lossone number saying how wrong the model currently is. Training is nothing but making it smaller.
optimiser stepthe moment the weights actually change, using the gradient of the loss. One step per batch, normally.
checkpointthe weights written to a file, so you can stop, resume, or go back to the best version.

The loop is always the same four lines: predict, measure the loss, work out the gradients, take a step. Everything else is bookkeeping around that.

PART 01Data and the loop

Dataset, DataLoader, and the five lines.

Dataset — three methods

class TabularDS(Dataset):
    def __init__(self, X, y):
        self.X = torch.from_numpy(X); self.y = torch.from_numpy(y).unsqueeze(1)

    def __len__(self):          return len(self.X)
    def __getitem__(self, i):   return self.X[i], self.y[i]

DataLoader then handles batching, shuffling and parallel loading:

DataLoader(ds, batch_size=64, shuffle=True,
           num_workers=8,            # roughly cores; 0 inside notebooks
           pin_memory=True,          # faster host -> GPU copies
           persistent_workers=True)  # do not respawn every epoch

Do the expensive work in __init__, not __getitem__. Tokenising or decoding per item, per epoch, is why so many GPUs sit at 10% utilisation.

Loss functions: use the fused one

# binary classification
model -> logits            + nn.BCEWithLogitsLoss()     # stable
model -> sigmoid -> probs  + nn.BCELoss()               # NaN waiting to happen

# multi-class
model -> logits            + nn.CrossEntropyLoss()      # includes softmax

Both fused losses combine the activation and the loss in one numerically stable operation. Applying the activation yourself first is the most common cause of a loss that suddenly becomes nan.

So your model's forward should return raw logits — and you apply sigmoid or softmax only when you need a probability to show someone.

Early stopping and a schedule

sched = CosineAnnealingLR(opt, T_max=EPOCHS)   # smooth decay, a good default

if auc > best: best, bad = auc, 0; save()
else:          bad += 1
if bad >= patience: break                     # stop paying for nothing
ScheduleShapeUse
CosineAnnealingLRsmooth decaya sane default
OneCycleLRup then downfast convergence from scratch
get_linear_schedule_with_warmupramp then decaytransformers, always

Warmup is not folklore for transformers. A full learning rate on step 1, applied to pretrained weights, damages them before training has begun.

PART 02Hugging Face

Standing on 100,000 GPU-hours you did not pay for.

Three lines to a pretrained model

from transformers import AutoTokenizer, AutoModelForSequenceClassification

CKPT = "prajjwal1/bert-tiny"       # 17 MB. Swap for bert-base, or a 7B model.
tok   = AutoTokenizer.from_pretrained(CKPT)
model = AutoModelForSequenceClassification.from_pretrained(CKPT, num_labels=2)
  • The tokeniser must match the checkpoint. A mismatch does not error — it silently degrades.
  • Save them together. A model without its tokeniser is unusable.
  • The classification head is newly initialised and random. That is what you fine-tune.
before fine-tuning: accuracy 0.534  f1 0.400   <- a random head
after  fine-tuning: accuracy 1.000  f1 1.000

1.000 there means the toy task was easy — 58 eval sentences from 24 templates. On real data, expect a number below 1 and be suspicious if you do not get one.

Fine-tuning is the same loop

for batch in train_dl:
    opt.zero_grad(set_to_none=True)
    out = model(**batch)          # pass labels= and the model returns .loss itself
    out.loss.backward()
    clip_grad_norm_(model.parameters(), 1.0)
    opt.step(); sched.step()

Trainer wraps exactly this, and for real work you should use it:

args = TrainingArguments(output_dir="out", num_train_epochs=4,
                        per_device_train_batch_size=16, learning_rate=5e-4,
                        warmup_ratio=0.1, report_to=[])   # [] or it may autolog
Trainer(model=model, args=args, train_dataset=tr, eval_dataset=ev).train()

Worth writing the loop once anyway. When Trainer does something surprising — and it will — you need to know what it was doing on your behalf.

When you have little data, or little memory

# freeze the body, train only the head
for p in model.bert.parameters():
    p.requires_grad = False

# gradient accumulation: a big effective batch on a small card
loss = loss_fn(model(xb), yb) / ACCUM      # divide so gradients scale correctly
loss.backward()                            # gradients ACCUMULATE
if step % ACCUM == 0:
    opt.step(); opt.zero_grad(set_to_none=True)
40 mini-batches of 16 -> 10 optimiser steps (effective batch 64)
Accumulation is free in maths terms and costs only wall-clock. It is how a 7B model fits on one consumer card.
Do not forget the divide. Without / ACCUM your effective learning rate is four times what you think.

PART 03Getting it out

Export, and prove it matches.

TorchScript and ONNX

# TorchScript: still PyTorch, no Python class needed
traced = torch.jit.trace(model.eval(), example_input)
traced.save("model_traced.pt")
torch.jit.load("model_traced.pt")          # no import of your code

# ONNX: leaves PyTorch entirely
torch.onnx.export(model, example, "model.onnx",
                  input_names=["features"], output_names=["logit"],
                  dynamic_axes={"features": {0: "batch"}},   # variable batch size
                  opset_version=17)

trace records one execution. Data-dependent if statements get baked in as whatever happened during tracing. Use torch.jit.script when the forward pass branches.

Forget dynamic_axes and your ONNX model accepts exactly batch size 1 forever.

Always diff the outputs

onnx_out  = sess.run(None, {"features": probe})[0]
torch_out = model(torch.from_numpy(probe)).numpy()

assert np.allclose(onnx_out, torch_out, atol=1e-5)
original -1.842269   torchscript -1.842269   max diff 0.00e+00
onnx vs torch                            max diff 1.19e-07

Two lines that catch a whole class of production bug: an export that runs happily and returns subtly different numbers.

Put this assertion in CI. It is the only test that checks the thing you actually deploy against the thing you actually trained.

And is the export worth it?

Measured, single-row, on CPU — the production case for most services. ONNX Runtime wins here because there is no Python in the hot path.

On large batches or a GPU the ranking can reverse. Measure your own shape before choosing; do not inherit someone else's benchmark.

Cheat sheet

# setup
seed_everything(42)                       # random, numpy, torch, cuda, PYTHONHASHSEED
DEVICE = pick_device()                    # probe with a real matmul

# data
class DS(Dataset): __len__, __getitem__   # heavy work in __init__
DataLoader(ds, batch_size=64, shuffle=True, num_workers=8, pin_memory=True)

# loop
model.train() / model.eval()
opt.zero_grad(set_to_none=True); loss.backward(); clip_grad_norm_(...); opt.step()
with torch.no_grad():  ...                # evaluation
nn.BCEWithLogitsLoss() / nn.CrossEntropyLoss()

# checkpoints
torch.save({"model": m.state_dict(), "opt": o.state_dict(), "epoch": e}, "best.pt")

Start tomorrow, in this order

  1. Put pick_device() at the top of your training script and print what it chose.
  2. Seed all four generators; log the seed with the run.
  3. Switch to checkpointing on validation improvement, and save the optimiser state.
  4. Export to ONNX and assert the outputs match. If they do not, you found a bug before production did.
  5. Measure latency in all three runtimes at your batch size before picking one.
