First: what is an API?

Two programs agreeing on how to talk to each other.

Without one

Your model lives in a notebook. Anyone who wants a prediction needs your Python, your packages, your file paths — and you, to run it.

With one

Your model lives behind an address. Anything that can send an HTTP request — a website, a phone app, Excel, another team's Java service — can ask it for a prediction and get an answer back.

API = Application Programming Interface. A contract: send me this shape, I will send you back that shape. Neither side needs to know how the other is written.

How a request actually travels

Four hops out, four back. The client can be anything that speaks HTTP. uvicorn is the process listening on the port. FastAPI checks the input before your code runs. The model was loaded once at startup, so a prediction costs milliseconds, not seconds.

What a request is made of

Diagram: MDN Web Docs (developer.mozilla.org) — CC BY-SA 2.5

  • method — what you want done: GET to read, POST to send
  • path — which thing: /predict, /health
  • headers — everything else: content type, who you are
  • body — the data itself, usually JSON, on a POST
  • the reply comes back with a status code and a body
  • 200 fine · 422 your input was wrong · 500 our fault

And what comes back

Diagram: MDN Web Docs (developer.mozilla.org) — CC BY-SA 2.5

The same shape in reverse. The status code is the part your caller checks first, and the one you are responsible for choosing correctly — a validation failure answered with 200 is worse than no API at all.

The problem — a model only you can run

Three questions you will be asked

"Can the website use it?"

A website cannot import your .pkl. It can make an HTTP request.

"What happens with weird input?"

Right now: a confident prediction from nonsense, or a stack trace. Both are bad answers.

"Which version made this prediction?"

If the answer is not in the response, you cannot debug a complaint from last Tuesday.

All three are answered by putting the model behind a small, well-described HTTP service — and by describing it in types.

REST, which is what this session builds

The most common style by a wide margin. One call contains everything:

The URL names a thing, not an action — /predict, not /doThePrediction.

The two REST rules a diagram cannot show

Every request stands alone

The server remembers nothing between calls. Whatever it needs to know, you send. There is no "logged-in" state sitting in memory on one machine.

That is what lets you run ten copies behind a load balancer, and restart any of them, without a caller noticing.

Bodies are JSON, and that is the whole protocol

No client library, no code generation, no schema to compile. Any language that can make an HTTP request can call your model.

curl -X POST localhost:8000/predict \
  -H "Content-Type: application/json" \
  -d '{"tenure_months": 2, "plan": "basic"}'

curl is enough to test the whole thing.

The other kinds, and when you meet them

KindHow it differsWhere it shows up
GraphQL one endpoint; the caller writes a query naming exactly the fields it wants, and gets precisely those back mobile and web front-ends tired of either too much data or five round trips
gRPC binary instead of JSON, with the message shape declared up front in a .proto file. Faster and stricter; not readable by hand service-to-service calls inside a company, where speed matters and humans are not reading the traffic
WebSocket the connection stays open and both sides can send at any time, instead of request-then-answer live dashboards, chat, streaming token-by-token output from a language model
webhooks inverted: you register a URL, and they call you when something happens "payment succeeded", "training finished" — anything you would otherwise poll for

A model service is almost always REST. One request in, one prediction out, nothing remembered between calls — which is exactly the shape REST is best at. Reach for WebSocket when you stream output, and gRPC when two of your own services talk and the JSON overhead starts to show.

WHYWhy an API

Four reasons, and one case where you should not bother.

Reason 1 — it is the only interface everything speaks

A model behind HTTP can be called by things that share nothing with your code.

Callers you get for free

  • a React front end
  • a nightly Airflow job
  • a Java service in another team
  • a spreadsheet, honestly

What you no longer ship

  • your Python version
  • your sklearn version
  • your preprocessing code
  • your laptop

One deployable unit with one interface. Everything else is someone else's problem, which is the point.

Reason 2 — the boundary is where bad data gets in

Every value from outside is a stranger's guess about what you wanted.

{"tenure_months": "twelve",   // a string
 "monthly_charge": null,     // missing
 "support_calls": -3,        // impossible
 "plan": "Gold ",           // not a plan, and it has a space
 "tenure": 4}                // a typo -- did they mean tenure_months?

Without validation each of those produces a prediction. A wrong one, delivered confidently, that nobody will notice for a month.

With a Pydantic model the request is rejected before your code runs, and the reply names the field that was wrong. You did not write that check or that message.

Reason 3 — one place for the boring essentials

ConcernWhere it lives once you have an API
which model version answereda field in every response
how long predictions takeone middleware, every route
what was asked and answeredone logger
is the service aliveGET /health
rolling back a bad modeldeploy the previous image
who may call itone dependency on the route

In a notebook, each of these is "somebody should really…". In a service they are a few lines that apply to everything.

Reason 4 — the documentation writes itself

That page is not something you maintain. FastAPI generates it from the same Pydantic classes that do the validation, so it cannot drift from the truth. Callers can try the endpoint in the browser before writing a line of code.

When you should not build an API

SituationBetterWhy
Scoring 50 million rows nightlya batch jobHTTP per row is pure overhead
One analyst, one spreadsheet, once a quartera scripta service you must operate is worse than a script you run
Predictions needed inside a database querySQL / UDFdo not cross the network for a join
Sub-millisecond, in-process latencyembed the modelHTTP costs more than your model does

"Real time" is often "within the hour" when you ask. Ask before you build a service that someone has to keep alive at 3am.

PART 01Building it

Three endpoints, one contract, real tests.

The three endpoints every model API needs

RouteForMust never
GET /healthload balancers, on-call humansbe slow, or lie about readiness
POST /predictthe actual workguess when the model is missing
POST /predict/batchthe caller who has 10,000 rowsbe an afterthought — someone always asks

And one you get free: /docs. Interactive, generated, always accurate.

Health checks earn their keep the first time a deploy half-fails: "alive but no model loaded" is a different problem from "process dead", and only a health route can tell you which.

Pydantic — declare what you accept

Describe the request as a class. Each field's type and range is the rule; anything that breaks a rule is rejected before your code runs.

from typing import Literal, Optional
from pydantic import BaseModel, Field, ConfigDict

class Customer(BaseModel):
    model_config = ConfigDict(extra="forbid")     # a typo is an error, not a shrug

    tenure_months:  int   = Field(ge=0, le=600)
    monthly_charge: float = Field(ge=0, le=10_000)
    support_calls:  int   = Field(ge=0, le=100)
    plan: Literal["basic", "plus", "pro"]        # anything else is rejected

This class is the API contract, the validator, and the documentation. One definition, three jobs.

extra="forbid" is the setting people skip. Without it, a caller sending tenure instead of tenure_months gets a silent default and a confidently wrong answer.

What that buys you, measured

# from the notebook -- real rejections, real messages
  negative tenure      -> rejected: ('tenure_months',) Input should be greater than or equal to 0
  no such plan         -> rejected: ('plan',)          Input should be 'basic', 'plus' or 'pro'
  missing field        -> rejected: ('support_calls',) Field required
  unexpected field     -> rejected: ('tenure',)        Extra inputs are not permitted

Four classes of bad input, four precise errors, zero lines of validation code.

Over HTTP these become 422 responses with the same detail, so the caller can fix their own bug without emailing you.

The path of one request

Load the model once — lifespan

Lifespan is FastAPI's startup/shutdown hook: everything before yield runs once when the server starts, everything after it runs once when it stops.

from contextlib import asynccontextmanager

STATE = {}

@asynccontextmanager
async def lifespan(app: FastAPI):
    STATE["bundle"] = joblib.load("app/model.joblib")   # startup: once
    yield
    STATE.clear()                                        # shutdown: clean up

app = FastAPI(title="Churn API", version="1.0.0", lifespan=lifespan)

The mistake this prevents: joblib.load() inside the handler. It re-reads the file on every request — tens of milliseconds each, for no reason, forever.

Bundle the version and feature order with the model, not just the estimator. The API needs to know the column order it must reconstruct.

The handler, and refusing to guess

The whole prediction endpoint. Note what it does when the model is missing: it says so with 503, rather than guessing or crashing.

@app.post("/predict", response_model=Prediction)
def predict(customer: Customer):              # plain def: predict() is CPU work
    b = STATE.get("bundle")
    if b is None:
        raise HTTPException(status_code=503, detail="model not loaded")

    frame = pd.DataFrame([customer.model_dump()])[b["features"]]
    proba = float(b["pipeline"].predict_proba(frame)[0, 1])

    return Prediction(churn=proba >= 0.5, probability=round(proba, 4),
                      model_version=b["version"], request_id=uuid4().hex[:8])
503, not 500, when the model is missing. It tells an orchestrator "not ready, try another instance" instead of "something exploded".
Never return a default prediction when the model failed to load. A silent 0.5 for every customer is far worse than an honest error.

The status codes an API actually needs

CodeMeansWhose fault
200here is your prediction—
422your JSON did not match the schemathe caller's — and FastAPI says exactly how
401 / 403who are you / you may notthe caller's
404no such routethe caller's
503alive but not ready — model still loadingnobody's, yet
500your code raisedyours

The distinction that matters operationally: 4xx means stop paging me, the caller is holding it wrong. 5xx means wake someone up. Getting these right is the difference between a useful dashboard and a noisy one.

Never leak a stack trace

One handler for anything unexpected: the full detail goes to your logs, the caller gets a generic message. A stack trace in a response is a security problem.

@app.exception_handler(Exception)
async def unhandled(request: Request, exc: Exception):
    log.exception("unhandled error on %s", request.url.path)   # full detail, for you
    return JSONResponse(status_code=500,
                        content={"detail": "internal error"})   # generic, for them
  • A traceback tells an attacker your file paths, library versions and code structure.
  • It also tells a legitimate caller nothing they can act on.
  • Log the detail with a request id; return the id, not the trace.

Testing — no server required

TestClient runs the app in-process. No port, no waiting, no cleanup — which is why it belongs in CI.

from fastapi.testclient import TestClient
from app.main import app

with TestClient(app) as c:            # the with-block runs lifespan startup
    assert c.get("/health").json()["model_loaded"] is True

    r = c.post("/predict", json={"tenure_months": 12, "monthly_charge": 60.0,
                                     "support_calls": 1, "plan": "pro"})
    assert r.status_code == 200 and 0 <= r.json()["probability"] <= 1

    assert c.post("/predict", json={..., "plan": "platinum"}).status_code == 422

Real routing, real validation, real responses — in-process. Fast enough to run on every commit, which means these tests will actually get run.

Four tests worth writing first: health reports the model loaded · a good request returns the promised shape · a bad request is 422 · a batch of N returns N.

How fast is it, actually?

Measured, not guessed — 60 real HTTP requests to a real uvicorn process in the companion notebook. The batch endpoint is 87× cheaper per customer because it makes one model call instead of a hundred.

Why batching wins so much

The same 100 predictions, two ways. One call over 100 rows pays the fixed costs once instead of a hundred times.

# 100 separate requests: 100x (HTTP + validation + DataFrame + predict)
for c in customers:
    requests.post("/predict", json=c)          # 8.32 ms each

# one request: 1x HTTP, one DataFrame, ONE predict call over 100 rows
requests.post("/predict/batch", json={"customers": customers})
# 9.62 ms total -> 0.096 ms per customer

Model libraries are built for arrays. predict on 100 rows costs barely more than on one; the per-request overhead is what you were paying for.

Put a bound on it. Field(max_length=1000) on the batch — an unbounded list is a way for one caller to exhaust your memory.

Advanced 1 — async def, and the mistake it invites

Use plain def

@app.post("/predict")
def predict(c: Customer):
    return model.predict(...)   # CPU work

FastAPI runs it in a threadpool. Correct for model inference and blocking libraries.

Use async def

@app.post("/enrich")
async def enrich(c: Customer):
    async with httpx.AsyncClient() as x:
        return await x.get(...)   # waiting on I/O

Right when the body genuinely awaits something.

The expensive mistake: async def containing blocking code — requests.get, time.sleep, a slow predict. It freezes the whole event loop, so every concurrent request waits. If the body has no await, use def.

Advanced 2 — who is calling?

A dependency that runs before the handler. Return normally and the request proceeds; raise and it never reaches your code.

import secrets
from fastapi import Depends, Header, HTTPException

def require_key(x_api_key: str = Header(default="")):
    # compare_digest, not ==, so timing does not leak the key
    if not secrets.compare_digest(x_api_key, API_KEY):
        raise HTTPException(status_code=401, detail="invalid or missing X-API-Key")

@app.post("/predict", dependencies=[Depends(require_key)])
def predict(c: Customer): ...
# no key -> 401 · wrong key -> 401 · correct key -> 200   (measured in the notebook)
  • Depends is FastAPI's whole extensibility story — auth, database sessions, feature flags.
  • A shared key is the minimum. For real systems use OAuth2/JWT — the dependency shape is identical.
  • Read the key from an env var. Never commit it.

Advanced 3 — middleware, CORS, background work

Middleware wraps every request, so this timing header costs one function and applies everywhere.

# every response carries its own timing -- cheap, priceless when things slow down
@app.middleware("http")
async def add_timing(request, call_next):
    t0 = time.perf_counter()
    response = await call_next(request)
    response.headers["X-Process-Time-ms"] = f"{(time.perf_counter()-t0)*1000:.2f}"
    return response

# a browser calling you directly needs CORS -- and be specific about origins
app.add_middleware(CORSMiddleware, allow_origins=["https://app.acme.com"],
                   allow_methods=["POST"])

# answer now, do the slow thing after the response is sent
@app.post("/predict")
def predict(c: Customer, bg: BackgroundTasks):
    result = score(c)
    bg.add_task(log_prediction, c, result)
    return result

allow_origins=["*"] on an authenticated API is a security bug, not a convenience.

Advanced 4 — versions and configuration

Two routers mounted at different prefixes: old callers keep working while new ones move.

Never break a caller

v1 = APIRouter(prefix="/v1")
v2 = APIRouter(prefix="/v2")
app.include_router(v1)
app.include_router(v2)

Add /v2; leave /v1 answering until the last caller has moved. Also return model_version in the body — the API contract and the model version are different things.

Config from the environment

from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    model_path: str = "app/model.joblib"
    api_key: str
    log_level: str = "INFO"

settings = Settings()   # reads env, validates

Validated config, and it fails at startup rather than at 2am on the first request.

Advanced 5 — running it in production

--reload is for your laptop only. In production you run several worker processes and let something in front handle TLS.

# development
uvicorn app.main:app --reload

# production
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4
gunicorn app.main:app -k uvicorn.workers.UvicornWorker -w 4 --bind 0.0.0.0:8000
KnobGuidance
--workersabout CPU cores — but each loads its own copy of the model, so watch memory
--reloaddevelopment only; it watches the filesystem
liveness vs readinessliveness = process up; readiness = model loaded. Do not conflate them
behind a proxynginx or an ingress terminates TLS; uvicorn should not
