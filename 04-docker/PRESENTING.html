Session 4 · DockerPresenting this without waiting for builds

The slides carry the measured numbers — four images, 1.5 GB down to 468 MB. You read those out. This page carries what you actually run: how to install Docker, a two-file example that builds in half a second and needs no downloads, and the handful of commands you will be asked about.

Read the big numbers. Run the small example.

The four images the slides compare took 6.0 minutes to build, and 351 of those 360 seconds were pip install with nothing on screen but scrolling layer hashes. That is evidence worth having — it is not worth watching.

So the live example has no dependencies at all. example/ is an API written against the Python standard library: two files, nothing to install, nothing to download, and a build you can run mid-sentence.

Installing Docker

Do this days before, not the morning of. On every platform the install ends the same way: a background daemon that does the work, and a docker command that talks to it.

Linux — Ubuntu, Debian, Mint

# Docker's own convenience script. Fine for a laptop; for a server use the apt repo instead.
curl -fsSL https://get.docker.com | sh

# so you do not need sudo for every command -- then LOG OUT and back in
sudo usermod -aG docker $USER

# start it, and have it start on boot
sudo systemctl enable --now docker

The one that catches everyone. usermod does not affect the shell you typed it in. Until you log out and back in you get permission denied while trying to connect to the Docker daemon socket. newgrp docker fixes the current shell if you cannot log out.

macOS

brew install --cask docker
# then launch Docker Desktop once from Applications -- the CLI does
# nothing until the whale in the menu bar says "running"

Or the .dmg from docker.com/products/docker-desktop. Pick the Apple silicon or Intel build to match your machine.

Windows

  1. Install WSL 2 first: wsl --install in an admin PowerShell, then reboot.
  2. Install Docker Desktop from docker.com, leaving "Use the WSL 2 based engine" ticked.
  3. Work from inside the WSL shell, not PowerShell. Files under /home/… in WSL build many times faster than the same files under /mnt/c/….

Then check it, on any platform

docker --version   # the client is installed
docker info       # the daemon is actually running -- this is the real test
outputDocker version 29.6.1, build 8900f1d

docker run hello-world needs the network. It is the classic check, but it pulls an image. If you are offline, docker info printing a server section proves the same thing.

The live path

Five steps, all measured on the machine this was written on. The slowest is one second.

1What a container is0.17 s

docker run --rm python:3.12-slim python -c "print('hello from inside a container')"
outputhello from inside a container

A whole Linux userland, started, used and thrown away faster than you can describe it. --rm deletes the container on exit.

2Build the image, in front of them0.99 s

# --no-cache so nothing is hidden: this is the build, start to finish
docker build --no-cache -t churn:demo .
output[+] Building 1.0s (8/8) FINISHED => [1/4] FROM docker.io/library/python:3.12-slim => [2/4] RUN useradd --create-home --uid 10001 appuser => [3/4] WORKDIR /srv => [4/4] COPY app.py . => exporting to image 0.3s => => naming to docker.io/library/churn:demo

Four steps, one second, no network. Read the numbers on the left out loud — [1/4], [2/4] — each one is a layer, and that is the whole mental model the rest of the session builds on.

3Run it, and call it0.09 s

# check the port is free FIRST -- see the note under this step
ss -ltn | grep :8500 || echo free
docker run -d --name demo -p 8500:8000 churn:demo
curl -s localhost:8500/health
curl -s -X POST localhost:8500/predict \
  -H 'Content-Type: application/json' \
  -d '{"tenure_months": 2, "monthly_charge": 130, "support_calls": 8}'
output{"status": "ok", "version": "1.0.0"} {"churn": true, "probability": 0.98, "version": "1.0.0"}

The moment it stops being a build exercise. Code, in a container, answering over HTTP — and the caller neither knows nor cares that it is Python inside.

Check the port, do not assume it. Writing this page, both 8000 and 8080 were already held by the editor. Docker then fails to bind, the container dies on the spot, and curl quietly answers from whatever else is on that port — which looks exactly like your app misbehaving. One ss -ltn first saves the whole demo.

4It is not running as root0.02 s

docker exec demo id
outputuid=10001(appuser) gid=10001(appuser) groups=10001(appuser)

The one people remember. A container that gets broken into is a much better day when the process inside is not root. Two lines in the Dockerfile: useradd, then USER.

5Layers — why the ordering rule exists0.02 s

docker history churn:demo --format 'table {{.Size}}\t{{.CreatedBy}}' | head -6
outputSIZE CREATED BY 0B CMD ["python" "app.py"] 0B EXPOSE [8000/tcp] 0B USER appuser 1.78kB COPY app.py . # buildkit 0B WORKDIR /srv

Point at the 0B column: metadata instructions cost nothing, and the only thing this image adds to its base is 1.78 kB of source. Add a pip install layer and that line becomes 350 MB — which is why its position in the file decides your rebuild time.

The commands you will be asked about

Docker has a few hundred flags and about ten commands that matter. These are the ten. Every output below is real, from the container built above.

Looking at what you have

docker images          # images on disk -- the recipes
docker ps              # containers running -- the processes
docker ps -a           # ...including the ones that exited
docker psCONTAINER ID IMAGE COMMAND STATUS PORTS NAMES 045b10a866ca churn:demo "python app.py" Up 10 seconds 0.0.0.0:8500->8000/tcp demo

This is the distinction people trip on. An image is a file on disk that does nothing. A container is one running instance of it. docker images lists recipes; docker ps lists meals. One image, twenty containers, is normal.

The default table is too wide for a projector. Ask for the columns you want:

docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'
outputNAMES IMAGE STATUS PORTS demo churn:demo Up 10 seconds 0.0.0.0:8500->8000/tcp

Finding out what went wrong

docker logs demo             # everything the process printed
docker logs -f --tail 20 demo   # follow it live, like tail -f
outputlistening on 0.0.0.0:8000 (version 1.0.0) "GET /health HTTP/1.1" 200 - "POST /predict HTTP/1.1" 200 -

When a container will not start, this is the first command, always. The error is nearly always in the last three lines of docker logs, and nearly never anywhere else.

# open a shell inside the running container and look around
docker exec -it demo bash
docker exec demo ls -A /srv   # or just run one command
outputapp.py

One file. That is the .dockerignore doing its job — the Dockerfile, the build script and the git history all stayed outside. Without it, all of them ship.

docker stats --no-stream   # CPU and memory, right now
docker top demo            # the processes inside
docker port demo           # which host port maps where
outputNAME CPU % MEM USAGE / LIMIT demo 0.01% 13.74MiB / 30.96GiB 8000/tcp -> 0.0.0.0:8500

13.7 MB of memory for a running HTTP service. Worth saying out loud if anyone still thinks a container is a virtual machine.

Stopping and cleaning up

docker stop demo      # polite: SIGTERM, then SIGKILL after 10s
docker start demo     # same container, running again
docker rm -f demo     # stop and delete the container
docker rmi churn:demo # delete the image

rm removes a container, rmi removes an image. One letter, and Docker will refuse the second while any container still uses the image — which is the error, not a bug.

# reclaim disk: stopped containers, unused networks, dangling images
docker system prune

# the same, plus EVERY image nothing is using. Read the prompt.
docker system prune -a

Say the warning out loud. prune -a on a work machine can delete images that took an hour to pull. It asks first — that prompt is the only thing between the room and a very quiet ten minutes.

Build one from scratch, in front of them

This is the demo that lands. Two files, a build, and a container answering — nothing hidden, nothing downloaded, about a minute end to end. Everything below is in 04-docker/example/, so you can also just open it.

1 · The two files

An API on the standard library — no requirements.txt, because there is nothing to install — and the recipe to package it.

app.py — trimmed to the shape

import json, math
from http.server import BaseHTTPRequestHandler, HTTPServer

def predict(f):
    score = (-1.5 + 0.35 * f["support_calls"]
                  + 0.02 * f["monthly_charge"]
                  - 0.04 * f["tenure_months"])
    return round(1 / (1 + math.exp(-score)), 2)

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):    # /health
        ...
    def do_POST(self):   # /predict
        ...

HTTPServer(("0.0.0.0", 8000), Handler).serve_forever()

A hand-written rule stands in for the model. Swap in joblib.load() and the container does not change in any way — which is the point worth making.

Dockerfile — all of it

FROM python:3.12-slim

# a container process should not be root
RUN useradd --create-home --uid 10001 appuser
WORKDIR /srv

# the code goes last, because it is what changes most often
COPY app.py .

USER appuser
EXPOSE 8000
CMD ["python", "app.py"]

Eight lines. Read them out in order — base, user, workdir, code, drop privileges, run — and the whole file is explained.

2 · Build it and run it

docker build -t churn:demo .
docker run -d --name demo -p 8500:8000 churn:demo
curl -s localhost:8500/health
outputbuilt in 0.99 s · 119 MB {"status": "ok", "version": "1.0.0"}

119 MB, and every byte of it is the -slim base — the application adds 1.78 kB. Compare that with the 1.5 GB on the slides: same idea, one bad base image apart.

3 · Change the code, rebuild

Edit one line of app.py in front of them — change the version string — and build again.

docker build -t churn:demo .
outputrebuilt in 0.57 s · 3 of 4 steps CACHED

Half a second, and three of the four steps said CACHED. Docker reran only the layer that changed and everything after it. Point at the word as it scrolls past — that is the layer cache, visible.

4 · What changes the moment you add dependencies

This example has none, which is why it is fast. A real service has a requirements.txt, and then the order of two lines decides everything:

The wrong way round

COPY . .
RUN pip install -r requirements.txt

Any edit to any file changes the COPY layer, so pip runs again. Every rebuild pays the full cost.

rebuild after a one-character edit: 110.6 s

The right way round

COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .

The expensive layer depends only on the file that rarely changes, so it survives every edit to your code.

rebuild after a one-character edit: 0.1 s

Same change, 1106× apart, decided by which line comes first. Both numbers are measured and both are on the slides. Do not reproduce them live — 110 seconds is a very long time in a room.

# tidy up when you are done
docker rm -f demo
docker rmi churn:demo

When it goes wrong

Nothing builds — no network

The example needs no network if python:3.12-slim is already on the machine. That is the one thing to pull in advance.

docker image ls python:3.12-slim

If that prints a row, you can present offline, all of it.

Docker is not available at all

Everything above is on the slides: the four measured sizes, Docker's own architecture and layer diagrams, and the cold-versus-warm chart. You lose the live curl against a running container — describe it, and show the output from this page instead.
