Session 4 · DockerPresenting this without waiting for builds

The notebook is the right thing to hand out — it really builds four images and measures them. It is the wrong thing to run live. This is the live path: five commands, and the slowest takes under two seconds.

Why not just run the notebook?

Every number in this page came from running the notebook, so nothing here is guesswork. What it cost: 6.0 minutes, and 351 of those 360 seconds were three image builds with nothing on screen but scrolling layer hashes.

The fix is not to cut the builds. They are the evidence. The fix is to run them the night before, and spend the room's time on the results.

Before the room

Open docker_tutorial.ipynb and Run All except the last cell.

That exception matters. The final cell deletes all four images and the sandbox — correct for a reader who does not want 3 GB left behind, exactly wrong for you. This page was written after finding out the hard way.

# confirm the four images survived
docker images --filter reference='churn:*' --format 'table {{.Tag}}\t{{.Size}}'
expectedTAG SIZE naive 1.63GB ignored 1.56GB slim 490MB multi 491MB

A question you will get. That says 1.63 GB where the slides say 1,557 MB — the same image. docker images counts in decimal (1 GB = 1,000 MB); the notebook converts the raw byte count into MiB. Both are right. Say so and move on.

The live path

Five steps. The badge on each is what it actually took on the machine this was written on.

1What a container is0.16 s

docker run --rm python:3.12-slim python -c "print('hello from inside a container')"
outputhello from inside a container

A whole Linux userland, started, used and thrown away, faster than you can describe it. --rm deletes the container on exit.

2The four images, side by side0.01 s

docker images --filter reference='churn:*' --format 'table {{.Tag}}\t{{.Size}}'
outputTAG SIZE naive 1.63GB ignored 1.56GB slim 490MB multi 491MB

This is the session's headline and it is one command. Same application, four Dockerfiles, 3.3× between the first and the last.

3Layers — why the ordering rule exists0.01 s

docker history churn:multi --format 'table {{.Size}}\t{{.CreatedBy}}' | head -8
outputSIZE CREATED BY 0B CMD ["uvicorn" "app.main:app" "--host" "0.0.… 0B HEALTHCHECK {Test:[CMD-SHELL python -c "impo… 0B EXPOSE [8000/tcp] 0B ENV MODEL_PATH=/srv/app/model.joblib PYTHONU… 0B USER appuser

Point at the 0B column: metadata instructions cost nothing. The bytes are in the two COPY layers further down, which is why their order decides your rebuild time.

4Run it, and call it1.6 s

# pick a port and check it is free FIRST -- see the note under this step
ss -ltn | grep :8500 || echo free
docker run -d --name demo -p 8500:8000 churn:multi
curl -s localhost:8500/health
curl -s -X POST localhost:8500/predict \
  -H 'Content-Type: application/json' \
  -d '{"tenure_months": 2, "monthly_charge": 130.0, "support_calls": 8, "plan": "basic"}'
output{"status":"ok","model_loaded":true,"model_version":"1.0.0"} {"churn":true,"probability":0.98,"model_version":"1.0.0"}

The moment it stops being a build exercise. A model, in a container, answering over HTTP — and the caller neither knows nor cares that it is Python inside.

Check the port, do not assume it. Writing this page, both 8000 and 8080 were already held by the editor. Docker then fails to bind, the container dies on the spot, and curl quietly answers from whatever else is on that port — which looks exactly like your app misbehaving. One ss -ltn first saves the whole demo.

5It is not running as root0.03 s

docker exec demo id
docker rm -f demo
outputuid=10001(appuser) gid=10001(appuser) groups=10001(appuser)

The one people remember. A container that gets broken into is a much better day when the process inside is not root. Two lines in the Dockerfile: useradd, then USER.

The numbers to read out, not reproduce

All measured by the notebook. Quote them from the slides; do not try to produce them in front of anyone.

Sizes are stable; times are not. The megabytes will match on any machine. The seconds are from one laptop and moved by 30% between two runs of the same notebook — quote them as roughly a hundred seconds against a tenth of one, and the point survives whatever your hardware does.

When it goes wrong

A build has to happen live

Do it during questions, not during an explanation — and force it cold so the number is honest.

time docker build --no-cache \
  -f Dockerfile.multi -t churn:demo .

About 2 minutes. Take questions while it runs; do not narrate scrolling output.

Docker is not available at all

Everything above is on the slides: the four measured sizes, Docker's own architecture and layer diagrams, and the cold-versus-warm chart. You lose one thing — the live curl against a running container — and the notebook ships with that output saved, so you can show it.
