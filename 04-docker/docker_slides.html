First: what is a container?

One folder holding your program and everything it needs to run — Python, the libraries, the system packages — that any machine can start in a second.

A container is not a virtual machine

A VM carries a whole operating system and boots for a minute. A container shares the host's kernel and starts in milliseconds. That is the entire difference in practice: same isolation of your files and processes, none of the weight.

Image versus container

The image is the file on disk — a recipe's finished result, read-only. The container is one running copy of it. One image, ten containers, same bytes.

Because it shares the kernel: a Linux image needs a Linux kernel underneath. On a Mac or Windows machine, Docker quietly runs a small Linux VM for you.

Container versus virtual machine

One layer is the whole difference. Look for Operating System on each side.

Diagram: Kubernetes documentation (kubernetes.io) — CC BY 4.0, cropped

Right: containers keep only the app and its libraries and share the host's kernel. Megabytes, and about a second.

WHYWhy containers

Three reasons, and one honest caveat.

Reason 1 — the environment travels with the code

A model is not just weights. It is weights plus the exact library versions that can load them.

# the failure everyone has had
>>> joblib.load("model.joblib")
InconsistentVersionWarning: Trying to unpickle estimator from version 1.6.1
when using version 1.3.0. This might lead to breaking code or invalid results.
  • Your requirements.txt lists what you asked for, not what got installed.
  • An image records what actually is installed, byte for byte.

The artifact you test is the artifact you ship. Not a recipe for building something similar.

Reason 2 — one interface for anything you run

docker run api:1.0.0        # FastAPI service
docker run trainer:1.0.0     # a training job
docker run etl:1.0.0         # the pipeline from session 5
docker run prom/prometheus   # somebody else's software, session 10

Your platform team learns one deployment mechanism instead of five. Kubernetes, ECS, Cloud Run and every CI system speak this.

It is also how you get software you did not write. Session 10 runs Prometheus and Grafana with no installation at all — that only works because they ship images.

Reason 3 — a rollback is a tag

docker run churn:1.4.0-a1b2c3d       # today, and it is misbehaving
docker run churn:1.3.0-9f8e7d6       # thirty seconds later, back to normal
Without imagesWith images
reinstall the old dependencies, hoperun the previous tag
"which commit was deployed?"the tag contains the SHA
staging drifts from productionthe same bytes in both

Only if you tag properly. latest is not a version and cannot be rolled back to. Tag with a version and the git SHA.

docker --version

docker run --rm hello-world
"Cannot connect to the Docker daemon" means the daemon is not running, or your user is not in the docker group. It is not a Dockerfile problem.
Docker group ≈ root. Anyone in it can mount the host filesystem into a container. Fine on your laptop; a decision on a shared server.

What "layers" actually means

An image is a stack. Each Dockerfile instruction adds one layer on top of the last, and Docker reuses a layer whenever nothing below it changed.

Docker docs — Apache 2.0

Read it bottom-up: the base OS first, your code last.

That order is deliberate. Your code changes many times a day; your dependencies change monthly. With requirements.txt low in the stack, a code edit rebuilds one cheap layer.

Reverse them and every one-line change reinstalls everything. Measured in this session: 0.1s against 162s.

Layers are shared between images

Diagram: Docker documentation (docs.docker.com) — Apache 2.0, © Docker, Inc.

Two apps on the same base share those layers, on disk and over the network — which is why the second image you pull is so much faster than the first.

PART 01Building an image

Naive first, then measured improvements.

The naive Dockerfile — and its three bugs

The Dockerfile almost everyone writes first. It works, and it is slow and huge for three reasons flagged in the comments.

FROM python:3.12                      # bug 1: the full image
WORKDIR /srv
COPY . .                              # bug 2: everything. bug 3: before pip
RUN pip install -r requirements.txt
CMD uvicorn app.main:app --host 0.0.0.0 --port 8000

It works. That is what makes it dangerous — you only find out later, when your CI takes ten minutes and your registry bill arrives.

naive image:  1557.0 MB   built in 173.9s

Every instruction is a layer. docker history churn:naive shows you which one is enormous, and it is almost always the pip install or the base.

Four Dockerfiles, measured

Every number here came from a real build in the companion notebook, on the same application. The last one also runs as a non-root user and has a health check.

Fix 1 — .dockerignore

A list of things Docker should not even send to the daemon. Same syntax as .gitignore.

# .dockerignore -- same syntax as .gitignore
.git
__pycache__/
.venv/
*.ipynb
notes/
Dockerfile*

The build context is everything Docker uploads to the daemon before building. COPY . . then puts it inside the image.

Measured: 65 MB saved from one file, on a small project. On a real repo with history, notebooks and a virtualenv it is routinely hundreds of megabytes — and a .env file you did not mean to ship.

It is also a security control. COPY . . without it has shipped plenty of credentials into public registries.

Fix 2 — a smaller base, and no pip cache

Two changes: a base image without the compiler toolchain, and telling pip not to keep its downloads inside the image.

FROM python:3.12-slim                 # same Python, no compiler toolchain
WORKDIR /srv
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt   # do not keep the downloads
COPY app/ ./app/
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

naive    1557.0 MB
slim      467.2 MB   (70% smaller)
Use the exec form of CMD — a JSON array. The shell form wraps your process in /bin/sh -c, which swallows signals, so docker stop waits ten seconds and then kills it.
Alpine is not automatically better. It uses musl, so many Python wheels do not exist and pip compiles from source — slower builds, occasionally subtle bugs.

Fix 3 — multi-stage

A stage is one FROM block. Build in the first, copy only the finished files into the second — so compilers and build tools never reach the shipped image.

# ---------- stage 1: build ----------
FROM python:3.12-slim AS builder
WORKDIR /srv
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# ---------- stage 2: run ----------
FROM python:3.12-slim
RUN useradd --create-home --uid 10001 appuser
WORKDIR /srv
COPY --from=builder /install /usr/local
COPY app/ ./app/
USER appuser
EXPOSE 8000
HEALTHCHECK CMD python -c "import urllib.request;urllib.request.urlopen('http://127.0.0.1:8000/health')"
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

The compiler is needed to install, never to run. Stage 2 copies only the installed packages, so build tooling never reaches production — smaller and a smaller attack surface.

A trap that costs an afternoon

COPY --from=builder /install /usr/local        # only the installed packages

ERROR: failed to compute cache key: failed to calculate
       checksum of ref ...: "/#": not found

That trailing comment is not a comment. Docker parses the rest of the line as more source paths, so it goes looking for a file called #.

COPY and ADD take a list of arguments, so a trailing # becomes one of them. Comments must be on their own line.
RUN and shell-form CMD pass the whole line to /bin/sh, which does treat # as a comment — which is exactly why the mistake is so easy to make.

This happened while writing this session. The error message names neither the line nor the real problem.

PART 02Making it fast

One reordering, a 450× difference.

Layer caching, measured

A code edit costs 0.1 seconds; a dependency edit costs 162. Which one you get is decided entirely by the order of two COPY lines.

The rule, and the reordering

How to time a build without fooling yourself

Two ways to fool yourself, both hit while building this session: timing a "cold" build on a warm cache, and re-running a cache demo whose file change is identical to last time — Docker still has that layer, so the slow step never happens.

# a benchmark whose starting state you do not control is not a benchmark
t_cold = build("Dockerfile.multi", no_cache=True)   # 75.4s
t_warm = build("Dockerfile.multi")                  #  0.2s
# ...then edit app code, rebuild:                        #  0.2s
# ...then edit requirements.txt, rebuild:                # 90.0s

The first version of this slide was wrong. It compared two Dockerfiles without --no-cache, on a warm cache, and reported that the wrong order was faster. The measurements were real; the conclusion was nonsense.

Lesson beyond Docker: when you benchmark anything with a cache in it, control the cache explicitly or you are measuring history.

PART 03Running it

The flags that matter.

Running a container

Each flag maps a piece of the outside world in: a port, an environment variable, a folder, and a limit on what it may consume.

docker run -d --name churn \
  -p 8080:8000 \                          # host:container -- without this, nothing reaches it
  -e MODEL_PATH=/srv/app/model.joblib \    # config by environment, never baked in
  -v ./models:/srv/models:ro \             # a new model without a new image
  --memory 1g --cpus 1.5 \                 # one container must not take down the host
  --restart unless-stopped \
  churn:multi

GET /health : {'status': 'ok', 'model_loaded': True, 'model_version': '1.0.0'}
POST /predict: 200 {'churn': True, 'probability': 1.0, 'model_version': '1.0.0'}
uid=10001(appuser) gid=10001(appuser)

That prediction came from inside a container — no Python involved on the host, and the process is not root.

Everyday commands

The five you will actually type. logs and exec are the two that answer "why is it behaving like that?".

docker ps                          # what is running
docker logs -f churn               # follow stdout -- your app's logs, unchanged
docker exec -it churn bash         # a shell inside it, for when you are confused
docker stats churn                 # live CPU and memory
docker stop churn && docker rm churn
docker system df                   # where your disk went
docker system prune -a             # reclaim it (careful: removes unused images)
Log to stdout, not to a file. Docker captures stdout; a log file inside a container disappears with it. This is the one convention worth changing your app for.
docker system prune -a deletes unused images. Fast way to reclaim 20 GB, and a fast way to delete the base image you were about to build on.

Compose — describe it instead of typing it

The same docker run flags, written down as a file instead of typed from memory.

# compose.yaml
services:
  api:
    build: {context: ., dockerfile: Dockerfile.multi}
    image: churn:multi
    ports: ["8000:8000"]
    environment:
      MODEL_PATH: /srv/app/model.joblib
    volumes:
      - ./app/model.joblib:/srv/app/model.joblib:ro
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request;urllib.request.urlopen('http://127.0.0.1:8000/health')"]
      interval: 30s
    deploy: {resources: {limits: {cpus: "1.5", memory: 1g}}}
    restart: unless-stopped

docker compose up -d      docker compose logs -f api      docker compose down

Session 10 adds Prometheus and Grafana to this same file. Three services, one network, one command — that is when compose starts earning its place.

Cheat sheet

# build and inspect
docker build -t app:1.0.0 .
docker build --no-cache -t app:1.0.0 .        # honest baseline
docker images / docker history app:1.0.0
docker image inspect -f '{{.Size}}' app:1.0.0

# run
docker run -d --name a -p 8080:8000 -e KEY=v -v ./m:/srv/m:ro   --memory 1g --cpus 1.5 --restart unless-stopped app:1.0.0
docker logs -f a / docker exec -it a bash / docker stats a
docker stop a && docker rm a

# compose
docker compose up -d / ps / logs -f api / down

# ship
docker tag app:1.0.0 ghcr.io/acme/app:1.0.0-$(git rev-parse --short HEAD)
docker push ghcr.io/acme/app:1.0.0-...

# housekeeping
docker system df / docker system prune -a

Start tomorrow, in this order

  1. Add a .dockerignore. One file, usually hundreds of megabytes.
  2. Move COPY requirements.txt above COPY .. Measure a rebuild before and after — it is the cheapest win in this session.
  3. Switch the base to -slim, add --no-cache-dir, and write both image sizes down.
  4. Add USER appuser. Root in a container is a habit worth breaking early.
  5. Tag with a version and a SHA, and move the build into CI.
