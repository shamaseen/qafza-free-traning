ETL pipelines
that survive Tuesday

Anyone can move data once. This session is about the second run.

Who this is for

  • You can read a CSV with pandas and write it to a database.
  • You have a script that does this on a schedule, and you are a little afraid of it.
  • You have at least once found duplicate rows in a report and not known why.

By the end you can

  • Make a job safe to run twice — the property everything else depends on
  • Process only what is new, without losing late-arriving rows
  • Refuse a broken batch instead of quietly corrupting a table
  • Recover from a half-finished load, and explain last night from a log

Companion notebook: etl_tutorial.ipynb.

The problem — nobody's first pipeline is wrong

Three questions that decide the design

What if it runs twice?

A retry, a backfill, a task that timed out after it already succeeded. It will happen.

What if yesterday's data arrives today?

Upstream was down; a device was offline; someone corrected a record. Do you lose it?

What if the export is broken?

Half the amounts are null. Do you load them, or refuse the batch?

A pipeline is not "extract, transform, load". It is idempotency, incrementality, validation and recovery — the ETL is the easy part.

Crash course — the three letters

StageJobRule
Extractread from the sourcenever destructive; never "clever"
Transformclean, reshape, derivea pure function: DataFrame in, DataFrame out
Loadwrite to the destinationone transaction, and safe to repeat
def transform(df: pd.DataFrame) -> pd.DataFrame:   # no db, no clock, no network
    out = df.copy()
    out["currency"] = out.currency.str.upper().str.strip()
    out = out[out.amount.notna() & (out.amount >= 0)]
    return out.drop_duplicates(subset=["event_id"], keep="last")

Why purity earns its keep: you can test the whole business logic with three hand-written rows in milliseconds, and a failure is reproducible from the input alone.

The middle is the only part that is yours. Extract and load are plumbing every pipeline has; the transform is where your business rules live, and the only stage worth unit-testing on its own.
Sources multiply. One file today, four APIs and a database next quarter — which is why extract is kept separate and dumb, and why the loader takes a key rather than trusting the order rows arrive in.

WHYWhy these four properties

Each one is a whole class of 3am problem.

Reason 1 — idempotency is the foundation

Running twice must leave the same result as running once.

# from the notebook -- the same file, loaded twice
append-only table after two runs : 942     # every row duplicated
upsert  table after two runs     : 471     # unchanged

Upsert = update-or-insert: if a row with that key is already in the table, update it; otherwise insert it. That one rule is what makes the second run harmless.

  • Backfills become safe — just run the range again.
  • Retries become free, so your orchestrator can be aggressive about them.
  • Reprocessing late data costs compute and nothing else.

Without it, every other technique in this session is dangerous. Rewinding a watermark to catch late rows would create duplicates instead of fixing them.

Reason 2 — full reloads stop scaling, quietly

RowsFull reloadIncremental
100 k20 s — fine2 s
10 M30 min — "it's a bit slow"4 s
500 Mhours — misses the morning report10 s

Nothing breaks. The job just gets slower every month until one day it does not finish before people arrive at work.

The fix is a single stored number: the high-water mark of what you have already processed.

Reason 3 — bad data is worse than no data

The job failed

  • An alert fires.
  • Somebody looks at it.
  • The table still holds yesterday's correct numbers.

Annoying. Recoverable.

The job loaded rubbish

  • No alert. It "succeeded".
  • Dashboards move. People make decisions.
  • You find out in a meeting, three weeks later.

Now you must find every downstream number that was wrong.

Prefer the loud failure. Validate at the boundary and refuse the batch.

Reason 4 — you will be asked what happened

dag_id       | logical_date              | task_id   | state
=============+===========================+===========+========
etl_pipeline | 2026-03-03T00:00:00+00:00 | extract   | success
etl_pipeline | 2026-03-03T00:00:00+00:00 | check     | success
etl_pipeline | 2026-03-03T00:00:00+00:00 | transform | success
etl_pipeline | 2026-03-03T00:00:00+00:00 | load      | success

You write none of this. Your orchestrator already records it, and it answers, at 8am, without archaeology:

  • did last night run at all?
  • which task failed, and on which attempt?
  • if it refused, exactly why?

Logs in a file are for debugging. A run history is for answering questions.

PART 01Building it

Four properties, in the order you should add them.

An orchestrator runs it — it is not the job

Your job owns

  • idempotency
  • the upsert and its key
  • validation rules
  • the transform logic

Airflow / Dagster / Prefect own

  • schedule and calendar
  • retries and alerting
  • dependencies between jobs
  • a UI and a run history

The mistake: putting business logic in the orchestrator's DAG file (a DAG is just the graph of which job runs after which). Now it can only run inside Airflow, cannot be unit-tested, and cannot be run by hand at 3am.

Keep the job a plain Python callable. The DAG should be a one-line wrapper. Everything on the right of this slide is what the next four slides stop you from writing.

What Airflow itself is made of

You write DAG files. A scheduler parses them and decides what to run; an API server serves the UI you watch it in; both agree through one metadata database.

Nothing of yours lives in there. Your job is a plain callable the DAG file calls; everything in this picture is what you stop maintaining by using an orchestrator.

Property 1 — make it idempotent

Idempotent means running the job twice leaves the same result as running it once. It is the property everything else here depends on.

from sqlalchemy.dialects.sqlite import insert as sqlite_insert

events = Table("events", meta,
    Column("event_id", Integer, primary_key=True),   # the natural key
    ...)

stmt = sqlite_insert(events).values(rows)
stmt = stmt.on_conflict_do_update(
    index_elements=["event_id"],
    set_={c: stmt.excluded[c] for c in cols if c != "event_id"})

with engine.begin() as conn:      # one transaction: all of it, or none
    conn.execute(stmt)
Pick the natural key carefully. The id from the source system, not a surrogate you generate — a surrogate is different on every run, so nothing ever conflicts.
No natural key? Hash the columns that identify a row. If you cannot identify a row, you cannot deduplicate it, and you cannot be idempotent.

Property 2 — incremental, without a watermark table

The DAG, in code

The three functions you already wrote, plus eight lines telling Airflow when to run them. The logical date is the whole trick: it is the watermark, and you did not store it.

from airflow.sdk import dag, task          # Airflow 3

@dag(schedule="@daily", start_date=START,
     default_args={"retries": 2})
def etl_pipeline():

    @task
    def extract(**context):
        day = (context["logical_date"] - START).days   # never now()
        return f"landing/events_day{day}.csv"

    load(transform(check(extract())))         # this line is the graph

# three days, from the notebook
471 clean rows -> events_day0.csv    2026-03-01 -> table total:  471
485 clean rows -> events_day1.csv    2026-03-02 -> table total:  939
494 clean rows -> events_day2.csv    2026-03-03 -> table total: 1415
# then day 2 again, as a retry:
table before retry 1415, after retry 1415

No watermark table, so nothing to lose. Re-run any day and you get that day's data, because the date came from the schedule and not from the clock.

Property 3 — validate at the boundary

What to check, and what to tolerate

CheckCatchesAction
required columns presentthe source changed its columnsrefuse the batch
row count within a sane rangetruncated or duplicated exportrefuse
null rate per critical columna broken join upstreamrefuse
values in an allowed seta new category nobody told you aboutrefuse
no timestamps in the futurea clock or timezone bugrefuse
duplicate idsupstream retriedtolerate — the upsert handles it
a few impossible amountsordinary messinesstolerate — drop the rows in transform

The distinction: row-level filtering for messiness you expect; batch-level refusal for change you did not.

Property 4 — recover cleanly

Two separate ideas: wrap the load in one transaction so a failure leaves nothing behind, and retry only the failures that are worth retrying. You write the first. You declare the second.

# 1. one transaction -- no half-finished loads to clean up by hand
with engine.begin() as conn:
    conn.execute(stmt)                 # exception here -> automatic rollback
rows before 1415, after the failed load 1415

# 2. retries: one argument, instead of a backoff loop you maintain
@task(retries=2, retry_delay=pendulum.duration(seconds=1))
def call_a_flaky_api(): ...
attempt 1 ...
ConnectionError: upstream API timed out
attempt 2 ...
succeeded on attempt 2

Never retry a validation failure. A refused batch will be refused identically four more times — you have turned one clear alert into four, and delayed it. Retry connections and timeouts; fail fast on contract errors.

Advanced 2 — bigger than memory

When the file will not fit in RAM, read it in chunks — or push the work into the database and stop moving rows through Python at all.

# stream it in pieces; each chunk is its own transaction
for chunk in pd.read_csv(path, chunksize=100_000, parse_dates=["occurred_at"]):
    upsert(transform(chunk))

# or push the work to the database and stop moving rows through Python
with engine.begin() as c:
    c.execute(text("""
        INSERT INTO events SELECT * FROM staging
        ON CONFLICT (event_id) DO UPDATE SET amount = excluded.amount
    """))

Start tomorrow, in this order

  1. Run your pipeline twice on the same input. If the table changes, stop and fix that. Nothing else matters until the job is idempotent.
  2. Put a primary key on the source's natural key; switch the load to an upsert in one transaction.
  3. Find every datetime.now() in a scheduled job; take the date from the run instead.
  4. Write five validation checks and raise on them: schema, row count, null rate, allowed values, no future dates.
  5. Delete your retry loop and your run-log table. Your orchestrator has both already.
  6. Keep the job a plain callable, so the DAG file stays a wrapper you can read in one breath.
