Distributed ML
with Ray

The same Python on one core, sixteen cores, or a hundred machines.

Who this is for

  • You have a loop that takes hours and a machine with cores sitting idle.
  • You have heard "just use multiprocessing" and found out why that is painful.
  • You would like to write the code once and decide the scale later.

By the end you can

  • Parallelise work with @ray.remote, and measure what you actually gained
  • Avoid the mistake that makes Ray slower than serial
  • Choose between a task and an actor, and say why
  • Distribute a PyTorch training loop without writing cluster plumbing

Companion notebook: ray_tutorial.ipynb.

The problem

What you have

for config in configs:      # 200 of them
    score = evaluate(config)   # 40 seconds each
# 2 hours 15 minutes, on one core
# while 15 cores do nothing

Why the obvious fixes hurt

  • threading — the GIL; no gain for CPU work
  • multiprocessing — pickling pain, awkward errors, no story for a second machine
  • a job array on a cluster — a rewrite, and a new deployment

Ray's proposition is narrow and useful: mark a function remote, and the same code runs on one machine or a hundred.

What Ray is, in one picture

Three layers. You write Python against the middle one.

What it actually bought, measured

1.59s to 0.38s on 16 cores — and note the curve bends. Sixteen tasks gave 5.6×, not 16×. That gap is the honest part of this session.

Why you never get your core count

CostRoughly
scheduling one task~1 ms

One small task measured 0.93× — slower than serial. If your unit of work is milliseconds, the overhead is the work. Batch: send 1,000 items per task, not one.

The rule of thumb: a task should take at least a few hundred milliseconds for the arithmetic to work in your favour.

WHYWhy Ray specifically

And the cases where you should not.

Reason 1 — two functions to learn

Three steps, and that is most of Ray: mark the function, call it with .remote(), collect the answers with ray.get.

@ray.remote                       # 1. mark it
def work(x): ...

refs = [work.remote(x) for x in xs]   # 2. submit -- returns immediately
results = ray.get(refs)                # 3. wait

That is the entire core API. Everything else — actors, Train, Tune, Serve — is built on those two calls.

And the escape hatch is one line: ray.init(address="ray://head:10001") and the same script runs on a cluster. No rewrite, no new framework.

Reason 3 — state can live beside the work

Ray earns its place when the work is CPU-bound, chunky, and either does not fit in one process or genuinely needs a second machine.

What ray.init() actually starts

Your code runs on the head node; workers do the work.

Diagram: Ray documentation (docs.ray.io) — Apache 2.0

Head node — your notebook or script. It calls ray.init().

Worker nodes — run the tasks. On a laptop, one machine is both.

Crash course — the four words Ray is built from

WordWhat it means
taska plain function marked @ray.remote. Calling it with .remote() runs it in another process, on another core.
referencewhat .remote() hands back immediately — a receipt, not a result. ray.get(ref) is where you wait.
actora class marked @ray.remote. Unlike a task it keeps state between calls, so a model is loaded once and reused.
object storeshared memory on each machine. Put a big array in it once with ray.put and every worker reads it without a copy being sent.

Task for work that just needs doing. Actor when something expensive has to stay loaded. That single distinction covers most of Ray.

PART 01Tasks and actors

The two primitives, properly.

Submitting is not running

Sixteen tasks submitted in milliseconds, because none of them has run. What comes back is a receipt; the waiting happens later.

refs = [work.remote(i) for i in range(16)]
submitted 16 tasks in 27.2 ms -- nothing has run yet
first ref: ObjectRef(c8ef45ccd0112571ffffffffffffffffffffffff0100000001000000)

results = ray.get(refs)        # NOW we wait

The split matters: you submit everything, then wait once. Calling ray.get inside the loop serialises your parallel program back into a sequential one.

# the classic mistake
for i in range(16):
    results.append(ray.get(work.remote(i)))   # waits for each. No parallelism at all.

The same mistake, drawn

Three tasks, three workers — only ray.get moved.

Diagram: Ray documentation (docs.ray.io) — Apache 2.0

Left: ray.get in the loop — the workers take turns.

Right: submit all, ray.get once — they run together.

Actors — state that stays warm

A class instead of a function. It loads the model once in __init__ and keeps it, so later calls skip that cost.

@ray.remote
class Scorer:
    def __init__(self, weights):
        self.w = weights          # imagine 500 MB of model, loaded ONCE
        self.n = 0

    def score(self, x):
        self.n += 1
        return float(np.dot(self.w, x))

pool = [Scorer.remote(w) for _ in range(4)]
refs = [pool[i % 4].score.remote(x) for i, x in enumerate(work)]
200 scores across 4 actors in 356 ms   ·   calls per actor: [50, 50, 50, 50]

That is the model-serving pattern, in six lines: load once per worker, spread requests across the pool. Ray Serve is this with autoscaling and HTTP attached.

Take results as they finish

pending = refs
while pending:
    ready, pending = ray.wait(pending, num_returns=1)
    handle(ray.get(ready[0]))

submission order: 0 1 2 3 4 5 6 7
completion order: 0 4 5 1 2 6 3 7        # measured

ray.get(refs) waits for the slowest. When task durations vary — and they always do — ray.wait lets you start work on the early results instead of sitting idle.

It is also how you build a progress bar that is not a lie.

Four changes to a training loop

Your existing training loop, with two wrappers added: one shards the data across workers, the other keeps their gradients in sync.

def train_func(config):                       # runs on EVERY worker
    dl = ray.train.torch.prepare_data_loader(dl)   # shards it: each worker gets a different slice
    model = ray.train.torch.prepare_model(model)   # wraps in DDP
    for epoch in range(epochs):
        ...                                        # your loop, unchanged
        ray.train.report({"loss": loss})           # instead of print

TorchTrainer(train_loop_per_worker=train_func,
             scaling_config=ScalingConfig(num_workers=2, use_gpu=False)).fit()

ADVANCEDBeyond the basics

Resources, failures, and the rest of the stack.

Asking for what you need

Ray schedules by what a task declares. Ask for two CPUs and half a GPU and it will not start until that is free.

@ray.remote(num_cpus=2, num_gpus=0.5, memory=2 * 1024**3)
def heavy(x): ...

@ray.remote(max_retries=3, retry_exceptions=True)
def flaky(x): ...
  • Resources are logical, not enforced. num_cpus=2 tells the scheduler how many slots to reserve; it does not stop your code using more.
  • num_gpus=0.5 genuinely works — two tasks share one card.
  • Tasks are retried on worker death by default; exceptions in your code are not, unless you ask.

Actors are not retried the same way. An actor that dies loses its state — which is the price of holding state at all.

Debugging table

The dashboard (include_dashboard=True, then localhost:8265) shows task timelines and which worker is doing what. It is the fastest way to see "workers idle".

Cheat sheet

# start / stop
ray.init(ignore_reinit_error=True, log_to_driver=False)
ray.init(address="ray://head:10001")     # a real cluster; nothing else changes
ray.cluster_resources(); ray.shutdown()

# tasks
@ray.remote(num_cpus=2, num_gpus=0.5, max_retries=3)
refs = [f.remote(x) for x in xs]         # submit everything first
ray.get(refs)                            # then wait once
ready, pending = ray.wait(refs, num_returns=1)

# big objects
h = ray.put(big); f.remote(h)            # once, not per task

# actors
@ray.remote class A: ...
a = A.remote(); ray.get(a.method.remote(x))
pool = [A.remote() for _ in range(4)]    # concurrency = pool size

# training
TorchTrainer(train_loop_per_worker=fn,
             scaling_config=ScalingConfig(num_workers=4, use_gpu=True)).fit()

Start tomorrow, in this order

  1. Find your slowest loop that is CPU-bound and independent per item.
  2. Time it serially and write the number down. Without it you cannot tell whether Ray helped.
  3. Add @ray.remote, submit all, ray.get once. Compare.
  4. If it got slower, your tasks are too small — batch until each takes a few hundred ms.
  5. ray.put anything large that every task needs.
  6. Only reach for a cluster when one machine is genuinely full.
