Feature management
with Feast

One definition of a feature, used by training and by serving.

Who this is for

  • You compute features in a notebook for training, and again in an API for serving.
  • You have wondered whether your training set accidentally contains the future.
  • Two teams in your company have both written "average order value in the last 30 days".

By the end you can

  • Define a feature once and read it from both training and serving
  • Build a training set that is point-in-time correct, and prove it
  • Serve features in under a millisecond
  • Say when a feature store is worth the operational cost, and when it is not

Companion notebook: feast_tutorial.ipynb.

Problem 1 — training/serving skew

Problem 2 — the training set contains the future

Why the second one is so easy to get wrong

# the join everybody writes first
labels.merge(current_features, on="driver_id")     # WRONG

It is one line, it runs, and the column names look right. What it actually does is attach today's feature values to last month's labels.

Label dateWhat the model needsWhat the naive join gives
3 March 09:00the value at 3 March 09:00the value now
5 March 14:00the value at 5 March 14:00the value now

This is the same leak session 1 measured at +0.245 accuracy, arriving through the feature layer instead of the preprocessing layer. It needs a timestamp on every feature value to fix — which is precisely what a feature store stores.

WHYWhy a feature store

Three reasons, and an honest cost.

Reason 1 — one definition, both sides

# features.py -- the only place this feature is defined
driver_hourly_stats = FeatureView(
    name="driver_hourly_stats",
    entities=[driver],
    ttl=timedelta(days=3),
    schema=[Field(name="conv_rate", dtype=Float32), ...],
    source=driver_stats_source,
)

# training            store.get_historical_features(entity_df, features)
# serving             store.get_online_features(entity_rows, features)

Measured in the notebook: offline and online values agree to five decimal places — not because someone kept two implementations in sync, but because there is only one.

Reason 2 — two access patterns, one source of truth

Reason 3 — features become reusable

Without a registry

  • three teams write "30-day average order value"
  • three slightly different definitions
  • nobody knows which one a model used
  • a fix has to be made three times

With one

  • feast feature-views list
  • owner and team in the tags
  • a model records the feature names it used
  • one fix, everywhere

This is the reason large teams adopt one — not latency. Latency you can solve with Redis. Agreement between teams you cannot.

What a feature store costs — and when to skip it

SituationVerdict
One model, one team, features computed in the same job that trainsskip it — you have no skew to remove
Batch scoring only, no online servinga table plus point-in-time SQL is enough
Features that are pure functions of the requestjust compute them; there is no history to store
Several models, shared entities, online servingworth it
You cannot answer "was our training set point-in-time correct?"worth it

It is infrastructure. A registry, an online store, a materialisation schedule, and a new failure mode: stale features that are not obviously stale. Adopt it for the skew and the reuse, not because it is on a diagram.

WordMeans
Entitythe thing features describe, plus its join key — a driver, a customer
Sourcewhere feature history lives, and which column is the timestamp
FeatureViewa named group of features, for an entity, from a source
Registrythe shared catalogue of all of the above
Materialisationcopying the latest values into the online store
TTLhow old a value may be before it counts as missing

PART 01Using it

Define, train, serve.

Define it once

# feature_store.yaml -- infrastructure, not logic
project: driver_ranking
provider: local
registry: data/registry.db
online_store: {type: sqlite, path: data/online_store.db}
offline_store: {type: file}

# features.py -- the contract
driver = Entity(name="driver", join_keys=["driver_id"])

source = FileSource(path=str(DATA), timestamp_field="event_timestamp",
                    created_timestamp_column="created")

driver_hourly_stats = FeatureView(name="driver_hourly_stats", entities=[driver],
                                  ttl=timedelta(days=3), schema=[...], source=source, online=True)

feast apply moves no data. It registers definitions, so every consumer resolves driver_hourly_stats:conv_rate to the same thing.

Two gotchas that cost an afternoon each

Timestamps must be tz-aware

df["event_timestamp"] = \
  df.event_timestamp.dt.tz_localize("UTC")

Naive timestamps survive the historical join — Feast localises them for you — but materialisation silently matches nothing, so the online store comes back full of None with no error anywhere.

Relative paths resolve against the CWD

DATA = Path(__file__).parent / "data" / "stats.parquet"
FileSource(path=str(DATA), ...)

Not against the repo directory. Run from one folder up and it cannot find the data — deriving the path from __file__ ends the problem.

Both of these happened while building this session, and neither produced an error message that pointed at the cause.

A training set that does not contain the future

entity_df = pd.DataFrame({
    "driver_id":       [1001, 1002, 1001, 1003],
    "event_timestamp": label_times,          # WHEN each label happened
    "selected":        [1, 0, 1, 1],
})

training_df = store.get_historical_features(
    entity_df=entity_df,
    features=["driver_hourly_stats:conv_rate", "driver_hourly_stats:acc_rate"],
).to_df()

Feast does an as-of join per row: for each entity and timestamp, the last feature value at or before it.

last value at or before 2026-03-03 09:00: 0.3986
what Feast returned:                      0.3986   -> no future value leaked

The notebook asserts this rather than trusting it, by finding the expected value in the raw history and comparing.

Serving, and what "fast" means here

# once, on a schedule: copy the latest values into the online store
feast materialize 2026-03-01T00:00:00 2026-03-11T00:00:00

# then, per request
store.get_online_features(
    features=["driver_hourly_stats:conv_rate"],
    entity_rows=[{"driver_id": 1001}]).to_dict()
p50 0.40 ms   p95 0.54 ms
An unknown entity returns None, not an error. Your serving code must decide what that means — silently substituting a default is how every new user gets scored as average.
Prefer feast materialize start end over materialize-incremental until you understand the window it picks. Getting it wrong fails silently, as an online store full of nulls.

The payoff, measured

Offline and online agree to 5 decimal places -- training/serving skew, eliminated.

Advanced 1 — features computed at request time

from feast.on_demand_feature_view import on_demand_feature_view
# NOT `from feast import on_demand_feature_view` -- that imports the MODULE, and
# calling it raises "TypeError: 'module' object is not callable"

request = RequestSource(name="trip_request",
                       schema=[Field(name="trip_distance_km", dtype=Float64)])

@on_demand_feature_view(sources=[driver_hourly_stats, request],
                        schema=[Field(name="trips_per_km", dtype=Float64)],
                        mode="pandas")      # be explicit, or 0.40 fails at apply
def trip_features(inputs):
    return pd.DataFrame({"trips_per_km": inputs.avg_daily_trips / inputs.trip_distance_km})

Why bother, rather than computing it in the API? Because then the transformation is in the registry, so the training job applies exactly the same one.

Advanced 2 — feature services and TTL

A named bundle per model

driver_ranking_v1 = FeatureService(
    name="driver_ranking_v1",
    features=[driver_hourly_stats[["conv_rate"]],
              trip_features])

Serving asks for the service, not a list of features, so the set cannot drift. Version it: v2 adds a feature while v1 keeps answering for the model in production.

TTL is a real decision

  • too short → training rows full of nulls
  • too long → you train on values that were badly stale
  • it is per feature view, because staleness differs per feature

A label older than the TTL returns NaN — correct, and honest.

Start tomorrow, in this order

  1. Find one feature computed twice — once in training, once in serving. That pair is your skew, and it is probably already costing accuracy.
  2. Ask whether your training set was built with point-in-time joins. If nobody knows, it was not.
  3. Define that one feature in a feature view and read it from both sides.
  4. Materialise on a schedule, and alert on staleness — a feature store's characteristic failure is serving values that are quietly old.
  5. Only then consider Redis, streaming sources, or a second team.
