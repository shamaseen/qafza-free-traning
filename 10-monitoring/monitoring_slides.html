The problem — nothing crashes

Three questions, and who can answer them

Is it up?

Any health check. Solved for decades.

Is it fast, and failing?

Needs metrics with history — this is the Prometheus part.

Is it still right?

Needs the prediction distribution, and eventually labels. Nothing gives you this by default.

A model service needs all three. Most teams have the first, buy the second, and never build the third — which is the one that decays.

The three metric types

Instrumenting, in one middleware

from prometheus_client import Counter, Histogram, Gauge, generate_latest

REQUESTS = Counter("api_requests_total", "requests", ["endpoint", "method", "status"])
LATENCY  = Histogram("api_request_duration_seconds", "duration", ["endpoint"],
                    buckets=(.001, .005, .01, .025, .05, .1, .25, .5, 1, 2.5))
INFLIGHT = Gauge("api_inflight_requests", "being handled right now")

@app.middleware("http")
async def observe(request, call_next):
    INFLIGHT.inc()
    t0 = time.perf_counter()
    try:
        response = await call_next(request); return response
    finally:
        INFLIGHT.dec()
        LATENCY.labels(endpoint=request.url.path).observe(time.perf_counter() - t0)
        REQUESTS.labels(endpoint=request.url.path, method=request.method,
                        status=str(response.status_code)).inc()

@app.get("/metrics")
def metrics(): return Response(generate_latest(), media_type=CONTENT_TYPE_LATEST)

Set your own buckets. The defaults reach 10 seconds, which is useless for an API answering in 15 ms — every request lands in the first bucket and your p95 is meaningless.

Labels: powerful, and a trap

# good: a handful of values
REQUESTS.labels(endpoint="/predict", method="POST", status="200")

# disaster: unbounded
REQUESTS.labels(user_id="48219")          # one time series per user
REQUESTS.labels(request_id=uuid4().hex)   # one per request, forever

Every distinct combination of label values is a separate time series stored forever. This is called cardinality, and it is how people take Prometheus down.

Label onNever label on
endpoint, method, status, model versionuser id, request id, email, raw path with ids

A rough rule: if you cannot name every possible value, it is not a label.

Prometheus pulls; you do not push

# prometheus.yml
global:
  scrape_interval: 15s

rule_files: [/etc/prometheus/alerts.yml]

scrape_configs:
  - job_name: churn-api
    static_configs:
      - targets: ["api:8000"]      # the service name, not localhost
  • Prometheus fetches /metrics on a schedule and stores the series.
  • Your app keeps counters in memory; it never talks to Prometheus.
  • If the app restarts, counters reset — and rate() understands that.

The first query to run, always: up. If it is 0, nothing else on your dashboard means anything.

The four queries you will actually use

# 1. throughput
sum(rate(api_requests_total[1m]))                          6.08 req/s

# 2. error ratio -- a share, not a count
sum(rate(api_requests_total{status=~"5.."}[1m]))
  / sum(rate(api_requests_total[1m]))                      1.3%

# 3. a percentile, from the histogram buckets
histogram_quantile(0.95,
  sum(rate(api_request_duration_seconds_bucket[1m])) by (le))   42.4 ms

# 4. the ML one: mean of a histogram
sum(rate(model_score_sum[5m])) / sum(rate(model_score_count[5m]))   0.496

Every number there was measured in the notebook against a live Prometheus scraping a live service.

rate before sum, never the other way round — summing counters across restarts then taking a rate gives you nonsense.

PART 02Alerting

Being told, instead of looking.

A rule that fires

groups:
  - name: churn-api
    rules:
      - alert: HighErrorRate
        expr: |
          sum(rate(api_requests_total{status=~"5.."}[1m]))
            / sum(rate(api_requests_total[1m])) > 0.05
        for: 10s                      # sustained, not a single scrape
        labels: {severity: critical}
        annotations:
          summary: "over 5% of requests are failing"

alerts now: [('HighErrorRate', 'firing')]

Measured, not described: the notebook sends 60 failing requests and waits for the rule to move from inactive to pending to firing.

for: is not optional. A condition true for one scrape is noise. Without it you will silence the alert within a week, and then it protects nothing.

What to alert on — and what not to

AlertDo not alert
error ratio above threshold, sustaineda single failed request
p95 latency against your real SLOa p99 spike at 3am with no users
up == 0 — it is unreachableCPU at 80% — that is a graph
predictions far from the training distributionevery small wobble
deployed model version ≠ expecteddisk at 60%

The test for every alert: what would I do at 3am? If the answer is "look at it in the morning", it is a dashboard panel, not a page.

What monitoring a model adds

QuestionMetricWhy it is invisible otherwise
Have the inputs moved?feature summaries, or the score meanthe service answers perfectly
Have the predictions moved?model_score histogramstill 200, every time
Is it still accurate?needs labels, which arrive lateryou cannot measure it live

That third row is the honest limit. Ground truth arrives days or weeks after the prediction, so you monitor proxies now and reconcile with labels later.

Do not let "we cannot measure accuracy live" become "we measure nothing". The score distribution is free, and it moves first.

Start tomorrow, in this order

  1. Add /metrics to one service. One middleware, three metrics, half an hour.
  2. Set the histogram buckets to your real latencies. The defaults are wrong for an API.
  3. Four panels: throughput, error ratio, p95, and one model-specific number.
  4. Write one alert — error ratio, with a for: — and check it reaches a human.
  5. Commit the dashboard JSON. A dashboard you cannot recreate is a dashboard you will lose.
  6. Only then add drift detection.
