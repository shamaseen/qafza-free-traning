Automation

Crash course — the words in this session

WordWhat it means
deploymenta class Ray Serve runs for you and puts behind an HTTP address.
replicaone running copy of that class. Three replicas = three processes answering the same URL, so one slow request does not block the rest.
autoscalingletting Serve add and remove replicas based on load, instead of you picking a number and hoping.
batchingcollecting requests that arrive at the same moment and running them through the model in one call — usually the biggest single speed win.
workflowon the CI side: a YAML file GitHub runs for you on a push, a pull request, or a schedule.
gatea step in that workflow that can fail, and therefore blocks the thing after it. A check that cannot fail protects nothing.

PART 01Ray Serve

A managed pool of actors, with HTTP.

What Serve actually manages

Serve's own architecture

A controller starts and watches everything, a proxy takes the HTTP in, and your class runs in replicas.

Read it as "what did I not write?" Your code is only the green boxes.

A deployment is a class

An ordinary class with two decorators: one says how many copies to run, the other lets it speak HTTP through FastAPI.

@serve.deployment(num_replicas=2, ray_actor_options={"num_cpus": 1})
@serve.ingress(api)                    # it speaks FastAPI -- same as session 3
class ChurnService:
    def __init__(self, artifact="model.joblib"):
        self.bundle = joblib.load(artifact)     # once per replica, at startup

    @api.post("/predict")
    def predict(self, c: Customer):
        ...

serve.run(ChurnService.bind(), name="churn", route_prefix="/churn")

requests answered per replica pid: {1905411: 33, 1905402: 27}

Measured: 60 requests, two distinct process ids. You declared num_replicas=2; you did not write a load balancer, a health check or a restart loop.

And validation still comes from Pydantic — a bad request is 422, exactly as in session 3. The contract does not change when the runtime does.

Autoscaling and batching, as configuration

Both are settings, not code you write. You state the range of replicas and the load you want each to carry.

@serve.deployment(autoscaling_config={
    "min_replicas": 1,
    "max_replicas": 4,
    "target_ongoing_requests": 5,      # scale out past this
})

@serve.batch(max_batch_size=32, batch_wait_timeout_s=0.02)
async def score_many(self, rows: list):
    # Serve collects concurrent calls into ONE list, so the model runs once
    return [float(p) for p in self.model.predict_proba(pd.DataFrame(rows))[:, 1]]

Session 3 measured that batching was 87× cheaper per customer — but you had to expose a batch endpoint and the caller had to use it. @serve.batch gets the same benefit from callers that keep sending one row at a time.

The trade-off is latency. batch_wait_timeout_s is how long a request may wait for company. Too high and quiet periods feel slow.

Composition — three deployments, one endpoint

One deployment holding handles to two others. Callers see a single URL; behind it, two models run and their answers are combined.

@serve.deployment
class Router:
    def __init__(self, risk, value):
        self.risk, self.value = risk, value        # handles to other deployments

    async def __call__(self, request):
        f = await request.json()
        r = await self.risk.remote(f)               # may run on another node
        v = await self.value.remote(f)
        return {"action": "call now" if r > .5 and v > .4 else "monitor"}

serve.run(Router.bind(RiskModel.bind(), ValueModel.bind()), route_prefix="/composed")
POST /composed -> 200 {'risk': 0.8, 'value': 0.75, 'action': 'call now'}

Each part scales independently. If the risk model is expensive and the value model is cheap, give them different replica counts — something a single monolithic service cannot do.

A class passed to @serve.ingress may not define __call__ — ingress is for FastAPI-routed classes, __call__ for raw requests. Mixing them fails at deploy time.

PART 02GitHub Actions

Start with the check, not the deployment.

The first workflow is not a deployment

A workflow is a YAML file GitHub runs for you. on: lists what triggers it — here, every push and every pull request.

It is the one that stops broken work reaching main.

name: validate
on:
  push: {branches: [main]}
  pull_request:                    # the one that actually protects main
  workflow_dispatch:               # adds a "Run workflow" button

jobs:
  decks-and-notebooks:
    runs-on: ubuntu-latest         # a fresh VM every time
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: {python-version: "3.11"}
      - name: every deck must be balanced and offline
        run: python - <<'PY' ...

This course ships that file. .github/workflows/validate.yml checks that every deck is balanced and has no external references, that no notebook contains stored error outputs, and that the README links every built session.

A check that cannot fail is decoration

if bad:
    print("FAILURES:", *bad, sep="\n  ")
    sys.exit(1)                    # non-zero fails the job. This line is the point.
ConceptMeaning
on:which events trigger it — push, PR, schedule, manual
runs-on:a clean machine; nothing from your laptop is present
uses:a prebuilt action, pinned — @v4, never @main
secrets.* / vars.*secrets are masked in logs; variables are not
exit codenon-zero fails the job. Everything else is a suggestion

The failure mode to avoid: a job that prints warnings and exits 0. It stays green for a year while the thing it was supposed to check quietly rots.

Retraining: the part everyone forgets

The full quality gate, line by line

The step that can say no. It compares the new model's score against the one in production and exits non-zero if it is worse.

- name: refuse to promote a worse model
  run: |
    python - <<'PY'
    import json, sys
    new  = json.load(open("metrics.json"))
    base = json.load(open("baseline.json"))
    delta = new["roc_auc"] - base["roc_auc"]
    print(f"new {new['roc_auc']:.4f} baseline {base['roc_auc']:.4f} delta {delta:+.4f}")
    if delta < -0.005:
        print("REFUSING to promote: the new model is worse."); sys.exit(1)
    PY

Ten lines between "trained" and "shipped".

Without it, a Monday cron will eventually promote a worse model — because data drifts, an upstream column changes, or a bug slips in. The first person to notice is a customer, three weeks later.

Automation does not remove human error. It removes the human who would have caught it — unless you encode what that human was checking.

The other five lines that make it safe

LineWithout it
concurrency: {group: retrain}two retrains race; one overwrites the other's model
environment: productionno human sees the change before customers do
permissions: id-token: writelong-lived cloud keys sitting in repo secrets
dvc pull at a pinned commit"which data trained this?" has no answer
image tagged ${{ github.sha }}you cannot roll back to a specific commit
on:
  schedule:
    - cron: "0 3 * * 1"          # 03:00 UTC Monday. Note: UTC, always.
  workflow_dispatch:
    inputs:
      reason: {description: why are you retraining by hand?, required: true}

# GitHub Actions
on: {push: {branches:[main]}, pull_request: , schedule: [{cron: "0 3 * * 1"}]}
runs-on: ubuntu-latest
uses: actions/checkout@v4 | actions/setup-python@v5
concurrency: {group: retrain, cancel-in-progress: false}
permissions: {contents: read, id-token: write}
environment: production                  # attach a required reviewer
sys.exit(1)                              # the only thing that actually fails a job

Start tomorrow, in this order

  1. Write the CI job that would have caught your last broken merge. Make sure it can fail.
  2. Add concurrency to anything that writes shared state.
  3. If you retrain on a schedule, add the gate today. Ten lines.
  4. Put the git SHA in the image tag, so a rollback is a tag rather than an investigation.
  5. Only then reach for Serve autoscaling — replicas are easy, and a bad model shipping automatically is not.
