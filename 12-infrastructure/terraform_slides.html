Why the Docker provider for a training session

Identical to a cloud provider

  • the init / plan / apply cycle
  • state, and everything about it
  • the dependency graph
  • variables, outputs, modules
  • drift, import, workspaces

Different

  • resource type names
  • no credentials to configure
  • resources appear in a second, not five minutes
  • nothing costs money
  • your mistakes are free

Learning it against Docker is a feature, not a compromise. You can run destroy forty times while learning. On AWS that is a bill and a nervous afternoon.

main.tf, part 1: which plugin to use

main.tf
# 1. The plugin (provider) this configuration needs
terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"        # the Docker provider, from the Terraform registry
      version = "~> 3.0"                    # any 3.x: a new major version could change behaviour
    }
  }
}
The terraform block holds settings for Terraform itself: here, the Docker provider, any 3.x version.

Part 4: a resource has a type and a name

👆 type👆 name
main.tf
# 3. What should exist. resource "TYPE" "NAME" -> its address is TYPE.NAME
resource "docker_image" "nginx" {
  name         = "nginx:1.27-alpine"        # Terraform pulls this image if it is missing
  keep_locally = true                       # destroy leaves the image file on disk
}
resource "TYPE" "NAME": the provider defines the type, you choose the name. This one is the nginx image.
resource "النوع" "الاسم": المزوّد يحدد النوع وأنت تختار الاسم. هذا المورد هو صورة nginx.

Part 5: how many copies, and their names

copiestemplate
main.tf
resource "docker_container" "web" {
  count = var.replicas                      # this many copies: web[0], web[1], ...
  name  = "tf-web-${count.index}"           # ${...} puts a value inside a string: tf-web-0
  image = docker_image.nginx.image_id       # uses the image above, so Terraform makes the image first
count makes copies: web[0], web[1], … and ${count.index} puts each copy's number into its name.
count يصنع نسخاً: web[0] و web[1]… و ${count.index} يضع رقم كل نسخة في اسمها.

Part 6: what it needs first, and its port

dependencyports
main.tf
resource "docker_container" "web" {
  count = var.replicas                      # this many copies: web[0], web[1], ...
  name  = "tf-web-${count.index}"           # ${...} puts a value inside a string: tf-web-0
  image = docker_image.nginx.image_id       # uses the image above, so Terraform makes the image first
 
  ports {
    internal = 80                           # nginx listens on port 80 inside the container
    external = 8081 + count.index           # open on this machine as 8081, 8082, ...
  }
}
Pointing at docker_image.nginx makes Terraform build the image first. ports opens 8081 on this machine.
الإشارة إلى docker_image.nginx تجعل Terraform يبني الصورة أولاً، و ports تفتح المنفذ 8081 على هذا الجهاز.

04 · The workflow: init → plan → apply

init
→

→

init once. Then plan to preview, and apply to make it real. Read every plan.

init downloads the provider

terminal
$ terraform init
- Installed kreuzwerker/docker v3.9.0 (self-signed, key ID 0DCE698927DAF8EC)
Terraform has been successfully initialized!
$ ls -a
.  ..  .terraform  .terraform.lock.hcl  main.tf
initonce per folder

Commit .terraform.lock.hcl, which pins the exact version. Never commit .terraform/.

init, and the file you must commit

PathCommit?What it is
.terraform.lock.hclyesexact provider versions + checksums
.terraform/nodownloaded plugins; recreate with init
*.tfyesyour configuration
terraform.tfstateno — remotewhat exists, including secrets
*.tfvars with secretsnouse a secret manager or env vars

Not committing the lock file means two engineers can silently get different provider versions, and one of them sees a plan that wants to replace everything.

plan is a preview: nothing has changed yet

terminal
$ terraform plan
  # docker_container.web[0] will be created
  # docker_image.nginx will be created
Plan: 2 to add, 0 to change, 0 to destroy.
+ create~ update- destroy-/+ replace

Read the symbol in front of each line. -/+ means destroy, then create: on real data, stop and check.

apply makes it real

terminal
$ terraform apply -auto-approve
Apply complete! Resources: 2 added, 0 changed, 0 destroyed.
$ docker ps
NAMES      PORTS
tf-web-0   0.0.0.0:8081->80/tcp
$ curl http://127.0.0.1:8081
<title>Welcome to nginx!</title>
applymake it real

A real container, answering on port 8081. Terraform wrote down everything it built.

tf-web-0

tf-web-2

-var changes one run. The file still says 1, so the next apply removes the extra two.

Variables with validation

Inputs with types and rules. A bad value is caught before anything is created, not halfway through.

variables.tf
variable "api_port" {
  description = "host port for the API"
  type        = number
  default     = 8082

  validation {
    condition     = var.api_port > 1024 && var.api_port < 65535
    error_message = "api_port must be an unprivileged port."
  }
}
PartWhat it does
variable "api_port"an input to the stack; with no default, Terraform asks for it
type = numbertyped, so the string "8082" is refused before anything is created
validation { condition }your own rule, checked at plan time — not halfway through an apply
error_messagewhat the person reads when it fails, so write it as advice

Measured in the notebook: replicas=1 → 3 added two containers; back to 1 destroyed two and left tf-web-0 untouched.

for_each is usually better than count — it keys resources by name, so removing the middle item does not renumber and recreate everything after it.

Outputs, and the graph you never wrote

outputs.tf
output "urls" {
  value = [for c in docker_container.web : "http://127.0.0.1:${c.ports[0].external}"]
}
terminal
$ terraform output
$ terraform graph

An output prints a value after apply, and terraform output reads it back later. terraform graph prints the order Terraform worked out from the references: the image before the container.

Outputs are also the interface between stacks: one stack publishes a VPC id, another consumes it.

Teams, environments, and not breaking production.

Shared state, and why it needs a lock

Once the state file is shared, two people can apply at the same time. The lock is what stops them from writing over each other.

backend.tf
terraform {
  backend "s3" {
    bucket         = "acme-tfstate"
    key            = "churn/prod.tfstate"
    region         = "eu-west-1"
    dynamodb_table = "tf-locks"       # the lock, not just the storage
    encrypt        = true
  }
}
PartWhat it does
backend "s3"where the state file lives — anywhere but a laptop
bucket / keythe bucket, and the path inside it: one key per stack, never shared
dynamodb_tablethe lock. One apply at a time, and the second one waits
encrypt = truestate holds secrets in plain text, so it is encrypted at rest

Two people applying at once without a lock corrupts state, and the recovery is manual and unpleasant. Shared storage without locking is worse than a local file, because it looks safe.

Do this on day two, not the day the second engineer joins.

Modules, environments, adoption

A module is a folder of Terraform you call with different inputs — the same shape for staging and production.

modules
# a module is the unit of reuse
module "api" {
  source   = "./modules/service"
  name     = "churn"
  replicas = 3
}

# separate environments, separate state
terraform workspace new staging
terraform apply -var-file=staging.tfvars

# adopt something that already exists
terraform import docker_container.web <container-id>

HabitWhy
Read every plan, especially -/+that is destroy-and-recreate, on real data
plan -out, then apply that filethe reviewed plan is the applied plan

prevent_destroy on stateful thingsa lifecycle block is cheaper than a restore

Cheat sheet

cheat sheet
# the cycle
terraform init                     # commit .terraform.lock.hcl
terraform fmt / validate           # cheap, in CI
terraform plan -out=tf.plan        # read it, all of it
terraform apply tf.plan            # apply exactly what was reviewed
terraform destroy

# state
terraform state list / show ADDR
terraform state mv OLD NEW         # rename without recreating
terraform import ADDR REAL_ID      # adopt existing infrastructure

# plan symbols
+ create   - destroy   ~ update in place   -/+ RECREATE   +/- create then destroy

# structure
variable / output / locals / module / data
count = n   |   for_each = toset([...])     # prefer for_each
lifecycle { prevent_destroy = true, create_before_destroy = true }

# teams
backend "s3" { ..., dynamodb_table = "tf-locks", encrypt = true }
terraform workspace new staging

Start tomorrow, in this order

  1. Pick the smallest real thing you own. Write it as one resource.
  2. plan, read it line by line, then apply.
  3. Move state to a remote backend with locking before anyone else touches the stack.
  4. Add prevent_destroy to anything holding data you cannot recreate.
  5. Put plan in CI on pull requests. A reviewed plan is the entire value.
  6. Do not try to import your whole estate in week one. One service, then the next.
