Infrastructure
as code

Terraform — describe what you want, review what will change, then let it happen.

Who this is for

  • Your infrastructure was created by clicking in a console, or by a script nobody trusts.
  • Nobody can say with confidence what is currently running.
  • "Recreate the staging environment" is a week of work.

By the end you can

  • Write, plan and apply a real configuration
  • Explain what state is, and why it matters more than the code
  • Read a plan — including the line that means "this will be destroyed"
  • Handle drift, variables, outputs and dependencies

Companion notebook: terraform_tutorial.ipynb — it uses the Docker provider, so everything is real with no cloud account and no bill.

The problem

How infrastructure usually exists

  • someone clicked it into a console in 2023
  • a wiki page, three quarters correct
  • a shell script that only works the first time
  • the person who set it up has left

What that costs

  • staging does not match production, so tests lie
  • nobody dares change anything
  • recovery time is measured in days
  • a security review cannot even enumerate what exists

Infrastructure as code makes the environment a reviewable artifact: in git, diffable, and recreatable from nothing.

Declarative is the whole point

Learning it against Docker is a feature, not a compromise. You can run destroy forty times while learning. On AWS that is a bill and a nervous afternoon.

PART 01The cycle

init, plan, apply — and state.

One resource, end to end

Four blocks and one command each. You describe what should exist; Terraform works out the calls to make.

terraform {
  required_providers {
    docker = { source = "kreuzwerker/docker", version = "~> 3.0" }
  }
}

resource "docker_image" "nginx" {
  name = "nginx:1.27-alpine"
}

resource "docker_container" "web" {
  name  = "tf-web"
  image = docker_image.nginx.image_id     # this reference IS the dependency graph
  ports { internal = 80, external = 8081 }
}

Plan: 2 to add, 0 to change, 0 to destroy.
Apply complete! Resources: 2 added, 0 changed, 0 destroyed.
HTTP 200 from the container Terraform created
PartWhat it does
terraform { required_providers }which plugin talks to which API, and at which version
~> 3.0take 3.x, never 4.0 — a major version may plan a replacement
resource "type" "name"the type is the provider's; the name is yours, and only you use it
docker_image.nginx.image_idreading another resource's attribute is the dependency: image first, container after
ports { internal, external }a nested block: port 80 inside the container, 8081 on your machine

You never wrote "pull the image, then start the container". The reference implied the order, and Terraform worked it out.

init, and the file you must commit

terraform init
Initializing provider plugins...
- Installing kreuzwerker/docker v3.0.2...
Terraform has been successfully initialized!
PathCommit?What it is
.terraform.lock.hclyesexact provider versions + checksums
.terraform/nodownloaded plugins; recreate with init
*.tfyesyour configuration
terraform.tfstateno — remotewhat exists, including secrets
*.tfvars with secretsnouse a secret manager or env vars

Not committing the lock file means two engineers can silently get different provider versions, and one of them sees a plan that wants to replace everything.

State — the file people understand last

serial: 3   resources: 2
  docker_container.web  -> id b738ba4741d1  (tf-web)
  docker_image.nginx    -> id sha256:6769d  (nginx:1.27-alpine)

State is the map from your resource names to the real objects. Without it Terraform does not know that docker_container.web is that container, so it would create a second one.

FactConsequence
it contains secrets in plain textremote backend, encrypted, access-controlled
two applies at once corrupt ityou need locking, not just shared storage
losing it is recoverableterraform import, one resource at a time

Never hand-edit state. terraform state mv / rm / import exist precisely so you never open that JSON.

Reading a plan

The plan is the review. Read the symbol at the head of each line, then the one summary line at the bottom — that is where a quiet deletion shows up.

SymbolMeans
+create
-destroy
~update in place, nothing is lost
-/+destroy, then recreate — the data goes with it
+/-create first, destroy after (create_before_destroy)
<=read a data source; changes nothing
+ network_data = (known after apply)
# the value does not exist until the thing does

+ labels { # forces replacement
# this attribute cannot be edited in place

Plan: 2 to add, 0 to change, 0 to destroy.
Plan: 1 to add, 0 to change, 1 to destroy.
# the second one is a replacement, counted twice

The words to stop at are forces replacement. Terraform will delete the thing and build a new one, and anything living inside it does not come back.

Run it again and nothing happens — that is the point

The same configuration applied twice. The second run reports no changes, because Terraform compares what exists against what you asked for.

terraform apply     # first time: creates
Apply complete! Resources: 2 added

terraform plan      # immediately after, no config change
No changes. Your infrastructure matches the configuration.

That output is the property everything else rests on. Terraform does not replay steps; it compares desired state to real state and closes the gap.

Which is why it belongs in CI. A job that can safely run on every merge — because if nothing changed, nothing happens.

PART 02Real configurations

Variables, outputs, dependencies, drift.

Variables with validation

Inputs with types and rules. A bad value is caught before anything is created, not halfway through.

variable "api_port" {
  description = "host port for the API"
  type        = number
  default     = 8082

  validation {
    condition     = var.api_port > 1024 && var.api_port < 65535
    error_message = "api_port must be an unprivileged port."
  }
}

resource "docker_container" "api" {
  count = var.replicas                          # N copies: api[0], api[1], ...
  name  = "${var.app_name}-api-${count.index}"
  ports { internal = 80, external = var.api_port + count.index }
}
PartWhat it does
variable "api_port"an input to the stack; with no default, Terraform asks for it
type = numbertyped, so the string "8082" is refused before anything is created
validation { condition }your own rule, checked at plan time — not halfway through an apply
error_messagewhat the person reads when it fails, so write it as advice
count = var.replicasmake that many copies of this one block: api[0], api[1], …
count.indexwhich copy this is — 0, 1, 2 — so each gets its own name and port
"${var.app_name}-api-${count.index}"interpolation: the value is placed inside the string

Measured in the notebook: replicas=2 → 3 added one container and left the other two alone; 3 → 1 destroyed two and left the survivor untouched.

for_each is usually better than count — it keys resources by name, so removing the middle item does not renumber and recreate everything after it.

Outputs, and the graph you never wrote

output "api_urls" {
  value = [for c in docker_container.api : "http://127.0.0.1:${c.ports[0].external}"]
}

terraform graph
14 edges in the graph, for example:
  docker_container.api -> docker_network.app
  docker_container.api -> docker_image.api

You never wrote "create the network first". docker_network.app.name appearing inside the container resource is what tells Terraform the order — and lets it create independent resources in parallel.

Outputs are also the interface between stacks: one stack publishes a VPC id, another consumes it.

Drift — when someone changes it by hand

Somebody deleted a container in the console. plan notices the difference and offers to put it back.

docker rm -f tf-web      # somebody "just fixes something quickly"
terraform plan
Plan: 1 to add, 0 to change, 0 to destroy.
terraform apply
docker_container.web: Creating... Creation complete
Use it deliberately: run plan on a schedule and alert if it is ever non-empty. A non-empty plan on production means something changed outside the process.
It cuts both ways. An emergency manual fix will be reverted by the next apply unless you also change the code. Tell the team that before it happens.

ADVANCEDBeyond the basics

Teams, environments, and not breaking production.

Shared state, and why it needs a lock

Once the state file is shared, two people can apply at the same time. The lock is what stops them from writing over each other.

terraform {
  backend "s3" {
    bucket         = "acme-tfstate"
    key            = "churn/prod.tfstate"
    region         = "eu-west-1"
    dynamodb_table = "tf-locks"       # the lock, not just the storage
    encrypt        = true
  }
}
PartWhat it does
backend "s3"where the state file lives — anywhere but a laptop
bucket / keythe bucket, and the path inside it: one key per stack, never shared
dynamodb_tablethe lock. One apply at a time, and the second one waits
encrypt = truestate holds secrets in plain text, so it is encrypted at rest

Two people applying at once without a lock corrupts state, and the recovery is manual and unpleasant. Shared storage without locking is worse than a local file, because it looks safe.

Do this on day two, not the day the second engineer joins.

Modules, environments, adoption

A module is a folder of Terraform you call with different inputs — the same shape for staging and production.

# a module is the unit of reuse
module "api" {
  source   = "./modules/service"
  name     = "churn"
  replicas = 3
}

# separate environments, separate state
terraform workspace new staging
terraform apply -var-file=staging.tfvars

# adopt something that already exists
terraform import docker_container.web <container-id>

Cheat sheet

# the cycle
terraform init                     # commit .terraform.lock.hcl
terraform fmt / validate           # cheap, in CI
terraform plan -out=tf.plan        # read it, all of it
terraform apply tf.plan            # apply exactly what was reviewed
terraform destroy

# state
terraform state list / show ADDR
terraform state mv OLD NEW         # rename without recreating
terraform import ADDR REAL_ID      # adopt existing infrastructure

# plan symbols
+ create   - destroy   ~ update in place   -/+ RECREATE   +/- create then destroy

# structure
variable / output / locals / module / data
count = n   |   for_each = toset([...])     # prefer for_each
lifecycle { prevent_destroy = true, create_before_destroy = true }

# teams
backend "s3" { ..., dynamodb_table = "tf-locks", encrypt = true }
terraform workspace new staging

Start tomorrow, in this order

  1. Pick the smallest real thing you own. Write it as one resource.
  2. plan, read it line by line, then apply.
  3. Move state to a remote backend with locking before anyone else touches the stack.
  4. Add prevent_destroy to anything holding data you cannot recreate.
  5. Put plan in CI on pull requests. A reviewed plan is the entire value.
  6. Do not try to import your whole estate in week one. One service, then the next.
