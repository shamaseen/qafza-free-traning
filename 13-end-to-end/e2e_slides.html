SESSION 13The whole thing

Twelve sessions built the parts. This one connects them, and then proves the connection holds.

Who this is for

  • You have a model in a notebook, a script that trains it, and an API somewhere.
  • Each piece works. Nobody can say which data produced the model that is live.
  • "Can you retrain last quarter's model?" is answered with a guess.

By the end you can

  • Take one run id and recover the exact code, data and score behind it
  • Wire DVC, MLflow, sklearn, FastAPI, Docker and CI into one chain
  • Name the seams where such a chain actually breaks, and check each one
  • Hand the system to someone else without a call

Companion notebook: e2e_tutorial.ipynb.

The question that decides whether you have a system

Point at the model serving production traffic and ask:

# Which data was it trained on?
# Which version of the training code?
# What did it score, on which split?
# Can you produce that exact model again, today?

Four questions. If any answer starts with "I think", the parts are not a system — they are a pile that currently happens to work.

The usual failure is not technical. Every tool here is installed and in use. What is missing is that nothing links them, so the links live in one person's memory.

What "end to end" actually means

Not a diagram with more boxes. A contract:

GivenYou can get back
a run idthe code commit, the data fingerprint, the metrics
a commit + fingerprintthe identical model, bit for bit
a live endpointwhich run id is answering, right now
a metric movingan alert, and the run to compare against

Every row is a lookup, not a conversation. That is the whole difference.

The chain

Every session contributed one piece

PART 01Version the input first

Nothing downstream is reproducible if the input is not identifiable.

Two commands, and the data becomes a name

dvc add data/raw.csv          # hash it, cache it, write a pointer
dvc remote add -d storage ...  # where the bytes live
dvc push                       # bytes go there, not into git
git add data/raw.csv.dvc      # git carries the pointer only

Measured in the notebook, on 5 000 rows:

data fingerprint: 977ddb47130abcf45cf9b16e2ccc74f7
git carries: 89 bytes instead of 109556

That 32-character string is the point. From here on, "the data" has a name that can be written down, compared, and demanded back.

The pipeline is a file, not a habit

# dvc.yaml
stages:
  train:
    cmd: python src/train.py
    deps:  [src/train.py, data/raw.csv]      # change either -> stale
    params: [test_size, random_state, n_estimators, max_depth]
    outs:  [models/model.joblib, run_id.txt]
    metrics:
      - metrics.json:
          cache: false                       # small, so keep it in git

dvc repro now decides whether anything needs to run. Nobody has to remember the order, and nobody can skip a step by accident.

PART 02One run, three tags

Params and metrics are the easy part. Provenance is the part that pays off.

Provenance is three tags

The third tag is the one people forget

commit = subprocess.run(["git", "rev-parse", "HEAD"], ...)
mlflow.set_tag("git_commit", commit)     # which code, allegedly
mlflow.set_tag("git_dirty", ...)         # whether that was true

A commit hash describes a run only if the working tree matched it. Train from a tree with uncommitted edits and git_commit points at code that never produced that model.

Worse than missing provenance is provenance that lies. A missing tag makes you careful. A wrong one makes you confident.

The notebook asserts git_dirty == "false" before trusting anything else. In CI this is free — a runner always builds a checked-out commit.

Found the hard way: the tool dirties the tree itself

The first version of that check called every run dirty. The cause was not a stray edit.

# inside the stage, during `dvc repro`:
$ git status --porcelain
 D metrics.json                  # nobody deleted it -- dvc did

dvc repro removes a stage's own outputs before rerunning it. Since metrics.json is cache: false, it lives in git — so for the duration of the run, git honestly reports a deleted tracked file.

OUTS = {"metrics.json", "run_id.txt", "models/model.joblib"}
changed = [l[3:] for l in status if l[3:] not in OUTS]

A provenance check has to know what its own tooling touches — otherwise it cries wolf, and the team turns it off.

Order matters: commit, then run

This bug cost a full debugging round, and it is invisible until months later.

Wrong

dvc repro
git commit -m "pipeline"

The run tagged itself with the previous commit — one that does not even contain dvc.yaml. Reproducing from it fails with dvc.yaml does not exist.

Right

git commit -m "pipeline"
dvc repro
git commit -m "lock and metrics"

The tag names a commit that contains the pipeline that produced the run.

CI gets this right without trying: it can only ever run a commit that already exists.

What the run recorded

run id: e1d76959c7a04cf7b3987f8270044bc8

params : {'test_size': '0.25', 'random_state': '42',
          'n_estimators': '200', 'max_depth': '8'}
metrics: {'roc_auc': 0.8874, 'accuracy': 0.8099, 'f1': 0.8129}

dvc_data_md5   = 977ddb47130abcf45cf9b16e2ccc74f7
git_commit     = 4e2c17fd93bbf9d84679f93500b3aadd6186eb7e
splitter       = GroupShuffleSplit(customer_id)
git_dirty      = false

The splitter tag is there because session 1's lesson has to survive being forgotten: customers repeat, so whole customers are held out. Recording how a score was measured is part of recording the score.

PART 03Serve it, and let it say what it is

An endpoint that cannot name its model is an endpoint you cannot debug.

The API answers the provenance question too

GET /health : {'status': 'ok', 'model_loaded': True, 'version': '1.0.0',
               'run_id': 'e1d76959', 'offline_roc_auc': 0.8874}
POST /predict: {'churn': True, 'probability': 0.9996, ...}
bad request -> 422

Three things in one response: it is up, it knows which run it is serving, and it remembers what that run scored offline — so a live score that drifts has something to be compared against.

422 is a feature. Session 3's Pydantic model rejects plan: "gold" and a negative tenure before they reach the model.

Provenance as a metric, so alerts can use it

model_info{run_id="e1d76959",version="1.0.0"} 1.0

Session 10 gave every request a counter and a histogram. This one line adds the thing those numbers are useless without: which model produced them.

# the alert that catches a deploy nobody announced
count(count by (run_id) (model_info)) > 1

Two run ids serving at once is either a careful canary or an accident. Both are worth knowing about.

PART 04Ship it

One image. The model arrives separately, on purpose.

Mount the model, do not bake it

docker run -d -p 8000:8000 \
  -v $PWD/models:/srv/models:ro \           # the model, mounted read-only
  --memory 1g --cpus 1.5 e2e-churn:1.0.0

Measured: 451 MB, multi-stage, non-root. No build time quoted here on purpose — that cache was warm, and a warm build time means nothing. Session 4 measures cold.

Baked in

Every retrain is a new image, a new registry push, a new deploy. The image and the model version are welded together.

Mounted

A new model is a new file and a restart. The image changes when the code changes, which is what a version should mean.

The cost: the container now depends on something outside itself. That is a real trade — pay it deliberately, and make /health fail loudly when the mount is missing.

PART 05The proof

Six months later, all you have is a string.

Travel back with nothing but a run id

r = mlflow.get_run(mystery_run)               # the only thing we kept
want_commit = r.data.tags["git_commit"]
want_data   = r.data.tags["dvc_data_md5"]

git checkout $want_commit                     # the code it ran
dvc checkout                                 # the data it read
dvc repro --force                            # run it again

Before doing that, the notebook deliberately breaks the world: 1 500 duplicate rows added, n_estimators 200 → 40, max_depth 8 → 2. A naive re-run cannot land on the old number.

Same run id in, same number out

Note the y-axis starts at 0.82 to make the gap visible.

recorded   roc_auc: 0.8874
reproduced roc_auc: 0.8874
difference        : 0.000000

What each link had to be right for that to work

  1. The data was fingerprinted, and the fingerprint was stored on the run.
  2. The pipeline was committed before it ran, so the commit tag is real.
  3. The tree was clean, and that was recorded rather than assumed.
  4. The split was seeded and the splitter recorded — a random split would have made the score unreproducible even with identical data and code.
  5. Every fitted step lived inside the Pipeline, so nothing leaked from a fold boundary that no longer exists.

Miss any one of the five and the proof quietly stops being a proof — it becomes two numbers that happen to be close. That is why the notebook asserts on the difference instead of printing it.

What this session does not give you

Said plainly, because a capstone is where overclaiming happens.

  • Nothing here ran in CI. The workflow from session 11 checks the repo; this notebook was verified on one machine. A real system runs the chain on a fresh runner.
  • No cloud. The DVC remote is a local folder; the registry is the local Docker daemon. The commands change, the argument does not.
  • No online monitoring loop. Session 10's Prometheus and Grafana are separate here. Wiring them permanently is the next step, not a finished one.
  • One model, one dataset, synthetic. The point is the chain, not the score.

The handover test

Hand the repo to somebody and leave. These are the questions they will ask.

Their questionWhat answers it
How do I get the data?dvc pull
How do I train it?dvc repro
What did it score?dvc metrics show, or the MLflow run
Which model is live?GET /health
How do I run the API?docker run, one line
Which commit made this model?the git_commit tag
Is that tag trustworthy?the git_dirty tag

Seven answers, none of them a person. If any answer is your name, that is the next thing to automate.

Cheat sheet

Data and pipeline

dvc add data/raw.csv
dvc push / pull
dvc repro
dvc repro --force
dvc metrics show
dvc metrics diff HEAD~1

Run

mlflow.set_tag("git_commit", ...)
mlflow.set_tag("git_dirty", ...)
mlflow.set_tag("dvc_data_md5", ...)
mlflow.get_run(run_id)

Recover a model

git checkout $git_commit
dvc checkout
dvc repro --force

Serve and ship

uvicorn app.main:app
docker build -t churn:1.0.0 .
docker run -v $PWD/models:/srv/models:ro
curl localhost:8000/health
curl localhost:8000/metrics

Start tomorrow, in this order

  1. Tag your next training run with git_commit, git_dirty and a data fingerprint. Ten lines, and it works retroactively for every run after today.
  2. Put the run id in /health. The next incident pays for it.
  3. Move the training command into dvc.yaml — even one stage. Now the order is in a file instead of a habit.
  4. Try to reproduce last month's model. Whatever stops you is your real backlog.

Do it in that order and each step is an afternoon. Do it after the incident and it is a quarter.
