Crash course: what Git actually does

Git stores snapshots of your text files and lets you name each snapshot.

git init                  # turn this folder into a repo
git add train.py           # stage: "include this in the next snapshot"
git commit -m "first model"  # snapshot, with a message
git log --oneline         # list snapshots
a1b2c3d first model
git checkout a1b2c3d      # time travel: folder becomes that snapshot

Mental model: a commit is a labelled photograph of your project. checkout walks back into the photograph.

Crash course: what a hash is

A hash is a short fingerprint computed from a file's bytes.

md5sum data.csv
aa0ebaab931a540d9ffe0a40a6563007  data.csv
  • Same bytes in → same fingerprint out, always.
  • Change one character → a completely different fingerprint.
  • 32 characters can therefore stand in for a 5 GB file.

Remember this one line. It is the whole trick behind DVC: store the fingerprint in Git, store the bytes somewhere else.

Why Git alone breaks on data

Git is built for text

  • It stores a diff of what changed per line.
  • A CSV or a .parquet or a .jpg has no useful lines.
  • So Git stores a whole new copy every time.

The result

  • 10 versions of a 1 GB file = a 10 GB repo.
  • git clone downloads all history, forever.
  • GitHub hard-rejects files over 100 MB.
git push
remote: error: File data/train.csv is 412.00 MB; this exceeds
remote: GitHub's file size limit of 100.00 MB

Everyone's workaround: a shared Drive folder called data_final_v3/. That is the bug we are fixing.

WHYWhy we use DVC

Three numbers that justify the tool to a manager — and to yourself at 3am.

Reason 1 — the repository stops growing with the data

Without DVC: ten revisions of a 1.2 GB CSV means a 12 GB repo, and every git clone — CI included — downloads all of it, forever. GitHub rejects the file at 100 MB anyway.
With DVC: Git stores an 88-byte pointer per revision. The repo stays in kilobytes; the bytes live in S3 and are fetched only when someone actually needs that version.

Reason 2 — switching versions stops being a coffee break

dvc checkout does not copy bytes — it links them out of the local cache (reflink, then hardlink, then symlink, then copy as a last resort).

The behavioural effect matters more than the seconds. When going back to last month's data is instant, people actually do it. When it costs ten minutes, they guess instead.

Reason 3 — hash-based caching skips work you already did

You edited train.py. DVC hashes every declared dependency, sees that ingest, clean and features have identical inputs, and skips them.

And it is not just speed: the skip is provable. The stage was skipped because its inputs hash the same — not because someone remembered it probably had not changed.

Reason 4 — a data change becomes reviewable

What a reviewer sees today

# Slack, Tuesday
"hey I updated the training data
 on the shared drive, retrain when
 you get a chance"

# no diff, no history, no rollback,
# no idea what actually changed

What a reviewer sees with DVC

This is the reason that survives contact with an auditor. The dataset change has an author, a date, a message and a review.

PART 01DVC

Data Version Control — Git for files too big for Git.

What DVC is

An open-source command-line tool that sits next to Git. It does not replace Git — it teaches Git to handle data.

The whole idea in one picture

Git carries the map. DVC carries the treasure.

Install and initialise

pip install dvc              # that is the whole install
pip install "dvc[s3]"       # add a cloud backend when you need one

cd my-project
git init                     # DVC needs a Git repo to live in
dvc init
Initialized DVC repository.

What dvc init created

.dvc/
  config      # where your remotes are configured (commit this)
  cache/      # the real data lives here (never committed)
  .gitignore  # DVC wrote this itself, so cache/ stays out of Git
.dvcignore    # like .gitignore, but for DVC's own scanning

Commit .dvc/config and .dvcignore. Everything else in .dvc/ is machine-local.

dvc add — the one command that matters

dvc add data/raw.csv
100% Adding...
To track the changes with git, run:
        git add data/raw.csv.dvc data/.gitignore

Three things just happened:

  1. The file's bytes were copied into .dvc/cache/, filed under its hash.
  2. A tiny text file data/raw.csv.dvc was written — the pointer.
  3. data/raw.csv was added to .gitignore, so Git will now ignore the big file.

You still see and open data/raw.csv normally. Nothing about your Python code changes.

Inside a .dvc pointer file

cat data/raw.csv.dvc

outs:
- md5: aa0ebaab931a540d9ffe0a40a6563007   # the fingerprint
  size: 78573601                            # bytes
  hash: md5
  path: raw.csv                             # where it belongs in the folder

That is 120 bytes of YAML. It is a normal text file, so Git versions it perfectly — diffs, branches, merges, pull requests, all of it.

This is the entire concept. Every other DVC command is bookkeeping around this file.

The two-command habit

# data changed?  DVC first, then Git.
dvc add data/raw.csv           # updates the hash in raw.csv.dvc
git add data/raw.csv.dvc
git commit -m "data: add March rows"
You want to version…Command
code, configs, the .dvc pointersgit add + git commit
datasets, models, big binariesdvc add

Train yourself on this pair now — it is 90% of daily DVC.

Remotes: sharing the actual bytes

A remote is just "somewhere else that can hold the cache". A folder on a NAS counts.

dvc remote add -d storage /mnt/shared/dvcstore   # -d = make it the default
# or: dvc remote add -d storage s3://my-bucket/dvc
# or: dvc remote add -d storage gdrive://<folder-id>

git add .dvc/config && git commit -m "add dvc remote"

dvc push       # upload cache -> remote   (like git push, for data)
dvc pull       # download remote -> cache -> your folder
dvc status -c  # what differs between me and the remote?

Teammate onboarding becomes two lines: git clone … then dvc pull. They get the code and the exact matching data.

Time travel — the payoff

# "give me the project exactly as it was 3 weeks ago"
git checkout a1b2c3d      # code + the .dvc pointers go back
dvc checkout              # the data files follow the pointers back

The #1 beginner mistake: running only git checkout and then wondering why the results changed. Always follow it with dvc checkout.

Why dvc checkout is instant

It does not copy gigabytes. It creates a link from the cache into your folder.

dvc config cache.type reflink,hardlink,symlink,copy
# DVC tries each in order and uses the fastest one your filesystem supports
  • Switching between two 50 GB dataset versions takes milliseconds, not minutes.
  • Ten branches sharing one dataset use disk for one copy.
  • Side effect: with hardlinks the file is read-only-ish. Edit it via a script and dvc add, don't edit in place.

Housekeeping: dvc gc deletes cached versions no commit refers to any more.

Level 2: pipelines

Versioning data is step one. Step two is versioning how the data was made.

Today

  • "Run cell 1, then cell 7, then prepare.py, then the notebook again."
  • Instructions live in someone's head or a README nobody updates.

With dvc.yaml

  • The recipe is a file in Git.
  • dvc repro runs exactly the steps that are stale.
  • Anyone can rebuild everything from a clean clone.

Defining stages

# dvc.yaml — write it by hand, it is just YAML
stages:
  prepare:
    cmd: python src/prepare.py            # what to run
    deps:                                 # inputs: change one -> stage is stale
      - src/prepare.py
      - data/raw.csv
    outs:                                 # outputs: DVC tracks these for you
      - data/prepared.csv

  train:
    cmd: python src/train.py
    deps:
      - src/train.py
      - data/prepared.csv                 # output of prepare = input here
    params:                               # values read from params.yaml
      - n_estimators
      - max_depth
    outs:
      - models/model.pkl
    metrics:
      - metrics.json:
          cache: false                    # small + JSON, so keep it in Git

Outputs listed under outs: need no dvc add — the pipeline owns them.

The DAG and dvc repro

dvc repro
Running stage 'prepare'...
Running stage 'train'...

dvc repro          # run it again, nothing changed
Stage 'prepare' didn't change, skipping
Stage 'train' didn't change, skipping

dvc dag            # draw the graph in the terminal

Edit only train.py? DVC re-runs train and leaves prepare alone. It compares hashes of every dep to decide.

dvc.lock and params.yaml

params.yaml — your knobs

n_estimators: 100
max_depth: 5
test_size: 0.2

Read it in Python with yaml.safe_load. Change a value, dvc repro notices and re-runs only what depends on it.

dvc.lock — the receipt

stages:
  train:
    cmd: python src/train.py
    deps:
    - path: data/prepared.csv
      md5: 9f2c…
    params:
      params.yaml:
        n_estimators: 100
    outs:
    - path: models/model.pkl
      md5: 3ab7…

Auto-generated. Commit it. It records exactly which inputs produced which outputs.

DVCLive — logging from inside your training code

Everything so far was the CLI. DVCLive is the Python side: a few lines in your training loop and every run becomes a DVC experiment, automatically.

pip install dvclive
from dvclive import Live

with Live() as live:                        # writes into ./dvclive/
    live.log_param("n_estimators", 150)      # an input you chose
    live.log_params({"max_depth": 8, "seed": 42})

    for epoch in range(20):
        loss = train_one_epoch()
        live.log_metric("train/loss", loss)      # a number you measured
        live.log_metric("val/acc", evaluate())
        live.next_step()                        # advance the step counter

    live.log_artifact("models/model.pkl", type="model", name="churn")
    live.log_sklearn_plot("confusion_matrix", y_true, y_pred)

Then look at it with the commands you already know: dvc exp show lists the run, dvc plots show draws the curves. No server, no UI to host.

What DVCLive gives you for free

The Live() knobs worth knowing

Live(
  dir="dvclive",          # where outputs go
  save_dvc_exp=True,      # each run -> a DVC experiment
  monitor_system=True,    # CPU/GPU/RAM/disk over time
  report="md",             # html | notebook | md | None
  resume=False,           # continue a previous run
  exp_name="rf-baseline",
)

What lands on disk

dvclive/
  metrics.json        # latest value of each metric
  params.yaml
  plots/metrics/      # one .tsv per metric, per step
  report.md           # if report= was set

Framework callbacks — one line, no loop edits

from dvclive.keras import DVCLiveCallback
model.fit(x, y, callbacks=[DVCLiveCallback()])

from dvclive.lightning import DVCLiveLogger
Trainer(logger=DVCLiveLogger())

from dvclive.huggingface import DVCLiveCallback

Also: PyTorch, XGBoost, LightGBM, CatBoost, Optuna, Ultralytics, Fast.ai, TensorBoard bridge, and more.

So DVC does have an experiment tracker. If you want run comparison and data versioning from one toolchain, this is the path — no second service to run.

Advanced 1 — data registries: reuse a dataset across repos

# take a file FROM another DVC repo, and keep the link tracked
dvc import https://github.com/acme/datasets data/customers.csv
# -> customers.csv.dvc records the source repo, the path AND the revision

dvc update customers.csv.dvc     # pull the newer upstream version, deliberately

# one-off download, no tracking (like curl, but DVC-aware)
dvc get https://github.com/acme/datasets data/customers.csv

# read it straight into Python, from any revision, without downloading the repo
import dvc.api, pandas as pd
with dvc.api.open("data/customers.csv", repo="https://github.com/acme/datasets",
                  rev="v2.1") as f:
    df = pd.read_csv(f)

The pattern: one repo is the data registry; model repos dvc import from it. Datasets get released and pinned like library versions.

Advanced 2 — templated and matrix stages

# dvc.yaml — stop copy-pasting near-identical stages
stages:
  featurize:
    foreach:                      # one stage per entry
      - city: amman
      - city: irbid
      - city: zarqa
    do:
      cmd: python src/feat.py --city ${item.city}
      deps: [src/feat.py, data/raw/${item.city}.csv]
      outs: [data/feat/${item.city}.parquet]

  train:
    matrix:                       # cartesian product -> 6 stages
      model: [rf, xgb]
      split: [a, b, c]
    cmd: python src/train.py --model ${item.model} --split ${item.split}
    outs: [models/${item.model}-${item.split}.pkl]

Values can also come from params.yaml: foreach: ${cities}. dvc repro still runs only the stale ones, and dvc repro -j 4 runs independent stages in parallel.

Advanced 3 — experiments at scale

# queue a grid without committing anything, then run it
dvc exp run --queue -S n_estimators=100 -S max_depth=4

Pair it with DVCLive (earlier slide) and the loop closes: the training code logs metrics per step, dvc exp run sweeps the params, dvc exp show ranks the results — all inside Git, no tracking server anywhere.

Advanced 6 — migrating an existing mess

# 1. a big file is already committed and the repo is now huge
#    remove it from history first (rewrites history - coordinate with the team!)

Advanced 8 — the run cache, and everyday surgery

Why a stage sometimes doesn't run at all

dvc repro
Running stage 'train'...
# ...revert the param, repro again:
dvc repro
Restored stage 'train' from run-cache
Skipping run, checking out outputs

DVC keeps a signature of every stage run in .dvc/cache/runs. Seen this exact combination of inputs before? It restores the outputs instead of recomputing them — even from a colleague's push.

dvc repro --no-run-cache      # force actual execution
dvc repro -f                  # force everything
dvc repro -s train            # one stage only

Everyday surgery

# stop tracking, keep the file
dvc remove data/raw.csv.dvc
# edit .gitignore to un-ignore it, then git add

# update tracked data (the two-command habit)
dvc add data/raw.csv && git add data/raw.csv.dvc

# rename / move a tracked file
dvc move data/raw.csv data/customers.csv

# freeze a stage so repro leaves it alone
dvc freeze train      # and: dvc unfreeze train

# what would change, without doing it
dvc status && dvc data status --granular

Advanced 9 — merge conflicts on data

Two branches both added rows. Git sees two different md5: lines and gives up. DVC ships a merge driver for exactly this.

# .gitattributes  (commit this)
*.dvc     merge=dvc
dvc.lock  merge=dvc

# register the driver once per clone
git config merge.dvc.name 'DVC merge driver'
git config merge.dvc.driver 'dvc git-hook merge-driver --ancestor %O --our %A --their %B'
What it handles: append-only directories — both sides added different files. DVC unions them.
What it refuses: the same file changed on both sides, or deleted on both. That is a real conflict and a human has to choose.

After merging dvc.yaml by hand, regenerate a clean lock with dvc repro — never hand-edit dvc.lock.

Advanced 10 — the rest of dvc.yaml

vars:                                   # values for ${} substitution
  - config/train.yaml                    # (not tracked as params)
  - codedir: src

stages:
  train:
    cmd: python ${codedir}/train.py --thresh ${models.us.threshold}
    wdir: .                              # run from a subdirectory
    desc: "Fit the classifier"            # shown by dvc stage list
    frozen: false                        # true = repro skips this stage
    always_changed: false                # true = always considered stale
    params:
      - n_estimators                     # from params.yaml
      - model.nn.batch_size              # a nested key
      - config.json:                     # a different file...
          - epochs                       # ...specific keys
      - hyper.toml:                      # YAML, JSON, TOML and .py all work
    outs:
      - models/model.pkl:
          cache: true                    # false = keep it in Git instead
          persist: true                  # survive between repro runs (checkpoints)
          push: false                    # never upload this one
          remote: bigfiles               # send it to a named remote
          desc: "trained sklearn model"

${} also unpacks dicts into CLI flags inside cmd: python train.py ${mydict} → --foo 'foo' --bar 1 --nested.baz 'bar'.

Advanced 11 — artifacts:, DVC's model registry

# dvc.yaml — annotate what matters, so people can find it by name
artifacts:
  churn-classifier:                      # the artifact ID
    path: models/model.pkl               # the only required field
    type: model                          # "model" is what the registry lists
    desc: 'Churn RF, trained on customers 2026-Q1'
    labels: [tabular, sklearn, churn]
    meta:
      framework: scikit-learn

Git tags become model versions. Combined with dvc import, one repo can publish data and models that other repos pin by revision — the same discipline you already use for libraries.

Advanced 12 — version notes and the rest of the ecosystem

DVC 2.x → 3.x (read before trusting a blog post)

  • Cache moved: .dvc/cache/<ab>/… → .dvc/cache/files/md5/<ab>/…
  • Migrate an old cache with dvc cache migrate
  • The dos2unix step before hashing was dropped, so text files can re-hash
  • hash: md5 was added to lock files — DVC 2.x cannot read 3.x files
  • Old data stays fetchable; new commits write to the new layout

Cheat sheet

dvc init                       # set up (after git init)
dvc add data/raw.csv           # track a file or folder
git add data/raw.csv.dvc       # commit the pointer, never the data
dvc remote add -d storage URL  # s3:// gs:// ssh:// gdrive:// or a path
dvc push / dvc pull            # upload / download the bytes
dvc status        / dvc status -c   # vs workspace / vs remote
dvc checkout                   # make files match the pointers (after git checkout)
dvc repro                      # run the stale pipeline stages
dvc dag                        # draw the stage graph
dvc metrics show / diff REV    # compare scores across commits
dvc plots diff REV --targets X # render comparison charts
dvc exp run --set-param k=v    # try something without committing
dvc exp show                   # table of every attempt
dvc gc -w                      # drop cache no commit refers to
dvc doctor                     # environment report for bug hunts
dvc remove / move / freeze     # untrack / rename / pin a stage
dvc remote modify --local …    # credentials, git-ignored
dvc artifacts get REPO NAME    # fetch a named model/dataset
dvc import-url URL PATH        # track an external source
dvc cache migrate              # 2.x cache -> 3.x layout
